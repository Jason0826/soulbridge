# 全系统审计 · 2026-11-02

> 触发：用户质问"改之前、改之后都要整体看一遍，怎么现在乱成这样了"。
> 审计结论：**不是结构自己长歪的，是执行失守**——八次改动每次只做了局部验收，没有一次整体 review。
> 工具：`node scripts/health-check.mjs`（机械部分已并入这个唯一入口，可重复跑）。

## 三、我上一轮说错的两件事（更正）

| 我说的 | 实际 | 结论 |
|---|---|---|
| "两套记忆并存：旧 memories 81 条还在写" | `memories` 只剩 **2 行**，写入路径还在但几乎不产生数据 | 问题不是"两套记忆"，是**写入路径没删干净**，读者还留着 |
| "12 个名词" | 活跃事实只有 **10 个 type_name**，状态只有 `none` / `superseded` | 碎片化在标签层存在，但状态层只有两态——这正是收敛要用的地方 |

**更正后的真问题**：`facts.status` 只有 `none` 和 `superseded`，没有"候选/生效/撤回"。
也就是说**判断一旦写进库就是生效的**——T1 说的"候选不生效"现在**没有字段可表达**。这是结构缺口，不是命名问题。

## 四、结构缺口的清单

| 缺口 | 证据 | 影响 |
|---|---|---|
| 没有生命周期状态 | `status` 只有 none/superseded | 候选、待核、生效无法表达；升格即生效 |
| 判断拆成多次调用 | 6 个模板、4 个队列 | 每加一个判断要动 prompt/parser/闸门/测试四处 |
| 队列实现重复 | 4 套 read/write/peek/commit/retry | 同一个数据丢失 bug 在三处各修过一次 |
| 冻结层没退场 | `turn_pairs` 97 行无写者，`memories` 2 行仍在读 | 统计口径不清（87 条纠正的误报就来自混用两套数据源） |
| 单文件过载 | 插件 2251 行 | 注入、4 队列、检测、合并、LLM 适配全在一个文件 |

## 五、收敛顺序（都是净减少）

| 步 | 动作 | 净效果 | 前置 |
|---|---|---|---|
| 0 | `health-check.mjs` 进流程（见第六节） | 每个改动都有整体数字 | 已完成 |
| 1 | 状态机：`status` 增加 `candidate`/`active`/`retracted` | 候选不生效成为可表达的事实 | 无（不建表，用现有列） |
| 2 | 通用队列模块 | 4 套 → 1 套，删约 90 行 | 无 |
| 3 | 分歧判断并进抽取（一次调用多段输出） | 不新增第 7 个模板 | 步 1（否则分歧只能产出"生效"） |
| 4 | 冻结层退场：`turn_pairs` 只读迁移完成即停止读；`memories` 写入路径删除 | 统计口径唯一 | 确认无消费者 |
| 5 | 插件拆文件 | 2251 行 → 4 个 ≤600 行 | 无（机械） |

**顺序理由**：状态机是"候选不生效"的前提，先有它，分歧才有意义；队列合并和拆文件是机械劳动，
放在功能稳定后一口气做。

## 六、把 review 变成可执行（流程补救）

**改之前（写进改动的说明里）**
1. 这个改动落在生命周期的哪一段？影响哪些表、哪些队列？
2. 它是否新增一个判断出口（prompt/parser）？能否并进已有的？
3. 它是否新增一个状态或概念？能否用现有的状态表达？
4. 失败时它会不会让某个数变得不可信（指标口径）？

**改之后（必须贴 `health-check.mjs` 的输出）**
1. 表：有没有新的"无写者/无读者"？
2. 队列/prompt：计数有没有增加？增加的理由是什么？
3. 词汇：`type_name` 数值增了没有？状态分布是否还只有两态？
4. 指标：这次改动让哪个数第一次可算，或让哪个数不再可信？

**这条规矩的判据**：一次改动的交付物里**必须有一行 review 输出**，没有就等于没做完。
（就像 `verify-installed.mjs` 之于部署：不是"我觉得装好了"，而是"跑出来的东西说装好了"。）
