# 2026-11-04 review：缺口收缩（顺序第 1 步）

> A9 要求每项做完整体看一遍。这一项是“顺序来”的第一步：把 223 条 open 缺口收缩到可回答的。

## 一、需求与数据

用户要的是“问一句她最近怎么样”，但如果库里挂着 223 条没人回答的缺口，关心就是噪声。

实测（改动前）：

```
gaps: open 223 · closed 0
其中 topic 以「日期不明：」开头的 154 条（69%）
opened 范围：2026-11-02 → 2026-11-04（两天内产生）
```

## 二、根因

`commitDrafts` 里这段：

```ts
if (holder === 'world' && written.atPrecision === 'unknown') {
  gaps.push(putGap({ topic: `日期不明：${statement}`, ... }))
}
```

**把“这条事实没有日期”当成了“有一个问题要问”。** 但这类问题永远关不掉：
用户不会为了每一条无日期的事实补时间，代码也没有任何关闭路径（`closeGap` 只有包装方法，
没有业务调用者）。

## 三、修法

1. **不再生成**：无日期是事实的属性（`atPrecision: unknown`），不是开放问题；
2. **关闭存量**：schema v12 把 `日期不明：` 前缀的 open 缺口关闭，记
   `close_reason='time-unknown-not-a-gap'`；
3. **加过期关闭**：`Soul.sweep()` 每次 pre-step 关闭 14 天没人回答的缺口，记
   `close_reason='expired'`；
4. `gaps` 表新增 `close_reason`，关闭不删除，保留主题与时间。

## 四、验证

```
core 292 测试（+2：v12 迁移映射、sweep 关旧留新）
插件 86（未改断言；pre-step 新增一次 UPDATE）
```

部署后核对：`open` 应从 223 降到 69（154 条日期不明被关），且新抽取不再增加这类缺口。

## 五、这次 review 自己的局限

- 只处理了“日期不明”这一类；另外 69 条是模型生成的语义缺口，尚未定义“什么算回答了一个缺口”，
  所以它们仍可能永远 open；
- `sweep` 的 14 天阈值是猜的，没有数据支撑——先跑一周看关闭量再调；
- 关闭能力目前只有“过期”一种，**没有“被回答”**——那需要语义判断，留给下一步（人物状态时
  一并设计）。
