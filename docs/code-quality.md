# 代码规范（可判定的）

> 这份文件管"代码写得对不对、读不读得懂"。交付流程见 [process.md](process.md)；
> 每一步的判定方式见那里，本文只管**代码质量**这一块。
>
> 判定原则：**能机械查的不靠人**（`health-check` 第 10 节），机械查不了的写成人审清单，
> 人审清单在代码审查（process 第 9 步）里逐条过。

## 一、四条总原则

| # | 原则 | 判定方式 |
|---|---|---|
| 1 | **可读性优先于聪明**：三个月后看不看得懂，比少写两行重要 | 人审：能不能不看注释说出这段在干什么 |
| 2 | **命名即文档**：名字说明不了功能，就把说明单独写出来（doc comment），不要靠长名字硬凑 | 机械：导出的函数必须有说明；人审：名字与内容是否一致 |
| 3 | **按变化轴解耦**：两个东西总是一起变就放一起，从不同时变就别耦合 | 人审：改一个需求要动几个文件？ |
| 4 | **失败必须显式**：失败要么抛出、要么返回可判别的结果，绝不吞成"看起来成功" | 人审 + 回归测试 |

第 4 条是今晚代码审查里最贵的一课：`collectText` 把宿主的 `finish(error)` 当成空串，
`operations ?? facts` 把一整类事实静默丢掉——**两种"看起来成功"都比报错贵得多**。

## 二、命名

| # | 规则 | 例 |
|---|---|---|
| N1 | 函数名 = 动词 + 对象，说明它做什么 | `applyProfileMerge`、`wasCorrectedTurn` |
| N2 | 布尔用 is/has/can/needs 开头 | `isDerivedProfileLine`、`hasMergeableGroup` |
| N3 | 值/结构用名词，不用动词 | `RetrievalPlan`、`ProfileGroup` |
| N4 | 名字里不出现类型噪音 | 不写 `strName`、`objFact` |
| N5 | 不用缩写，除非是领域公认的（id、url、sql） | 不写 `profMgr`、`cfg` |
| N6 | **名字装不下功能，就在函数上方写一段说明**：为什么存在、边界在哪、失败时怎样 | 见 `isDerivedProfileLine` 的注释 |

N6 是用户明确要求的一条：**命名不能解释功能时，说明要分开写**——不是把名字拉长到一句话。

## 三、函数与解耦

| # | 规则 | 判定 |
|---|---|---|
| F1 | 一个函数只做一件事；"顺便"做的第二件事必须拆出去 | 人审 |
| F2 | 函数 ≤ 60 行，参数 ≤ 4 个（超出先问是不是设计错了） | 机械（WARN） |
| F3 | 纯逻辑与 I/O 分离：解析、判定、评分是纯函数；读写集中在边界 | 人审 + 已有实践（`scoring.ts`、`consolidate.ts`） |
| F4 | 不返回 `null` 表示"失败"和"没有"两种意思；两种都要能区分 | 人审 |
| F5 | 多语句写库必须在一个事务里；单写者假设必须写进注释或类型 | 人审（审查项已有“无事务”这条） |
| F6 | 循环里不查库；一条查询能解的不要 N+1 | 人审（审查项已有索引建议） |

## 四、错误处理

| # | 规则 |
|---|---|
| E1 | `catch` 不允许"只记日志然后继续"——要么重试、要么降级、要么抛出，且**要说清降级成什么** |
| E2 | 吞掉异常的地方必须有注释说明为什么安全，否则视为 bug |
| E3 | 模型调用失败与"模型说没有"必须可区分（今晚 `collectText` 的教训） |
| E4 | 上限、超时、重试次数都是**实测出来的**，写清依据（例：`LLM_TIMEOUT_MS` 注释里有 p99 数据） |

## 五、定义与配置

| # | 规则 |
|---|---|
| D1 | 名词、常量、枚举、格式、默认值只在 `packages/core/src/config/` 声明一次；代码只做解码 |
| D2 | config 里不许有函数、分支、循环（`health-check` 第 9 节 FAIL） |
| D3 | 同一件事只允许一个表示；引入新表示时旧表示必须在同一改动里退场，或登记 `retirements.json` |
| D4 | prompt 里的输出示例必须能过对应解析器（golden test） |

## 六、测试

| # | 规则 |
|---|---|
| T1 | 修 bug 必须带一条**会红的测试**：先把修复去掉确认它红，再装回去 |
| T2 | 测行为，不测源码字符串；只有"防止某个写法回来"时才允许源码级断言，并在注释里说明 |
| T3 | 一个测试只断言一件事；名字说清场景（"a JSON-shaped draft is not silently dropped"） |
| T4 | 不写"看起来覆盖了"的测试：测试数据要能走真实路径（今晚 T1 的测试教训：直接插库绕过了写入路径） |

## 七、人审清单（代码审查时逐条过）

来自 [Google eng-practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html)
与 [Claude Code Review 参考](https://cdn.jsdelivr.net/npm/@georgedong32/pi-review@0.8.4/reference/claude-code-review.md)，按我们的情况裁剪：

1. **设计**：这段改动该不该存在？现在这个位置对不对？
2. **正确性**：边界、并发、空值、失败路径。
3. **复杂度**：有没有更简单的写法；有没有为了通用而过度设计。
4. **测试**：新增行为有测试吗；测试会红吗。
5. **命名**：名字是否描述了它做的事（N1–N6）。
6. **注释**：解释"为什么"，不解释"做了什么"；过时的注释比没有更糟。
7. **可读性**：能不能不看注释读懂；有没有隐藏的耦合。
8. **一致性**：和已有代码的分工、错误处理、命名风格一致吗。

## 八、审查的置信度（采纳 Claude Code Review 的做法）

每条发现打一个置信度，只把 ≥80 的报出来：

| 分 | 含义 |
|---|---|
| 0 | 误报，或**本来就有**的问题（不是这次改动引入的） |
| 25 | 可能对，但无法验证；纯风格问题 |
| 50 | 确实存在但很轻微 |
| 75 | 已验证、确实重要 |
| 100 | 确定，有直接证据（能复现/能跑出来） |

**明确的非发现**（不报）：本次改动没碰到的旧问题、格式/导入类问题（工具会做）、
"再抽一层会更好"这种口味建议、作者没改的行上的问题。

这条正好治我们第一轮审查的病：40 条里有重复和夸大，标 ✅/⏳ 是对的，但**应该带分数**。

## 十、工具纪律（一次例外都没有）

| # | 规则 | 为什么 |
|---|---|---|
| W1 | **改代码只用 `edit` / `write` 工具**。PowerShell 只用于只读命令、git、构建、测试 | 字符串替换会在三种地方炸：单引号里的反引号 `\n` 不转义、嵌套引号让脚本解析失败、编码不对把中文写成乱码。三次真实事故，三次都是想"只改一个字符串" |
| W2 | 批量替换即使"只是文档"，也用 `edit` 逐处改 | 编码损坏和引号解析与文件类型无关 |
| W3 | 别人（或过去的自己）说"已经出过这个错"时，**先改工具，不要先写一条新的记忆** | 这条规则本身就在记忆里躺了很久，还是被绕过——说明触发点不在记忆，在动手那一刻 |

W1 现在不是靠自觉：`health-check` 第 11 节扫**这次改动的行**，出现字面 `\n`、
U+FFFD、GBK 乱码特征就 FAIL。记录在案的判据：

```
✓ [体检] 这次改动的行没有替换/编码损坏的痕迹
```

## 十一、机械检查（`health-check` 第 10 节）

```
导出函数没有说明        → WARN（N6）
函数 > 60 行            → WARN（F2）
参数 > 4 个              → WARN（F2）
`: any`                  → WARN
console.log             → WARN（日志走 log()）
```

其余规则靠人审清单 + 代码审查，**不假装机器能全查**。
