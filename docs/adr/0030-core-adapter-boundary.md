# ADR 0030：core 与适配器的边界

- 状态：Accepted
- 日期：2026-11-01
- 关联：[ADR 0001](../adr/0001-soul-layer-only.md)（只做 soul 层）、[ADR 0019](0019-repo-conventions.md)、[ADR 0027](0027-code-vs-model-boundary.md)、[ADR 0029](0029-extraction-is-the-models-job.md)

## 背景

抽取接进插件后，它一直没有真正跑起来。查下来是**同一个守卫写在了两层**：

```
插件:  if (text.length < 4) return;   // 我改掉了
core:  if (text.trim().length < 4) return rules;   // 还在
```

结果：插件放行，core 静默回落规则，模型一次没调过，而日志看不出异常。

这不是疏忽，是**边界没定义**——"多短算不值得抽"这件事，插件觉得该自己管，core 也觉得该自己管。

## 判断规则（三问）

| 问题 | 归属 |
|---|---|
| 需要知道宿主事件（轮次、静默、会话、工具调用）吗？ | **适配器** |
| 是一个**策略**（花不花调用、阈值、重试、并发、预算）吗？ | **适配器** |
| 是**语义或结构不变式**（能不能写、写了算不算数、如何校验）吗？ | **core** |

## 分工表

| 能力 | core | 适配器 |
|---|---|---|
| 记忆模型：实体 / 事实 / 槽位 / 缺口 | ✅ | |
| 抽取的**结构**：模型调用形态、校验、合并操作 | ✅ | |
| 写入门禁：去重、实体消解、拒绝并说明原因 | ✅ | |
| 取数原语：实体式、穷举式、时间窗、排序 | ✅ | |
| 告诉调用方"我走了哪条路"（`reason`） | ✅ | |
| 何时触发抽取（轮结束 / 静默 / 手动） | | ✅ |
| 这段文本值不值得抽（长度、纯应答） | | ✅ |
| 模型从哪来、超时、重试、并发 | | ✅ |
| 日志、trace、指标、告警 | | ✅ |
| 存储位置、配置读取、版本兼容 | | ✅ |
| 注入时机与宿主事件绑定 | | ✅ |

## 由此产生的两条硬规则

1. **core 不放阈值。** 任何"多短/多少条/多长时间"的判断都是策略，归适配器。
   （现有的 `RECALL_CANDIDATES` 是资源保护上限，属于"最坏情况不能失控"，保留；它不是语义判断。）
2. **适配器必须留痕。** 跳过、回落、失败都要记录原因（`reason` 字段或日志）。
   **静默跳过等于没实现**——这一次就是被它骗了一小时。

## 为什么 core 要保留 `reason`

`reason` 不是策略，是**可观测性**：`rules-mode` / `no-model` / `model-failed` / `model-empty`。

core 是唯一知道"为什么走了规则"的地方，它不说，适配器只能猜。可观测性属于不变式，不下放。

## 后果

**正面**

- 同一个判断只有一处，不会两层漂移
- 换宿主只改适配器，core 行为不变（thesis P3 的前提）
- 跳过/回落有据可查

**负面**

- 每个适配器都要重复实现"值不值得"的策略（成本）
- core 的测试不能再依赖"长度"这类宿主假设

## 验收（可执行）

```
1. 全局搜索 core 源码：没有 length / 阈值类判断出现在 extract/commit 路径
2. 任何一次 extract 调用，日志里都有 by 与 reason
3. 同一句"做"：插件判定有实质内容 → 调模型；core 不再拦截
```

## 不做的

- 不在 core 里加"省 token"逻辑（那是适配器的钱）
- 不让适配器直接写库（必须走 commitDrafts）
- 不用重复守卫兜底（重复即漂移）
