# ADR 0011：质量门禁

- 状态：Accepted
- 日期：2026-10-27
- 相关：`docs/quality.md`、ADR 0004

## 背景

前身项目用一条很硬的质量红线维持了两年：`cargo build` 零警告、零 `unsafe`、`main.rs < 1500` 行、二进制 < 8MB。它之所以有效，是因为**每条都可自动检查**。

本项目需要等价物：同样的可检查性，但目标换成"可替换、可测试、可审计、隐私、成本"。

## 备选

1. 只靠 code review 与约定：不可执行，一定会漂。
2. 全套重型工具（ESLint + Prettier + 覆盖率门槛）：对 3 千行的项目过重，且引入依赖。
3. **九条可自动检查的门禁 + 五条人工评审清单**。

## 决定

选 3。门禁（进 CI）：

| # | 门禁 | 检查方式 |
|---|---|---|
| G1 | `tsc --noEmit` 零错误 | `npm run typecheck` |
| G2 | 公共 API 无 `any` | 类型检查 + 人工抽查 |
| G3 | `core` 只 import `node:` | 依赖检查脚本 |
| G4 | 每个动词有降级测试 | 测试名约定 `degrade:*` |
| G5 | 不变量测试（注入必有 used / 预算不超 / 不截断） | `node --test` |
| G6 | 对宿主返回 Result，内部抛带 code 的错误 | 测试断言 |
| G7 | 日志默认关闭、不含正文 | 代码审查 + 一个负向测试 |
| G8 | core < 3000 行，单文件 < 300 行 | 统计脚本 |
| G9 | 运行时依赖为 0 | `package.json` 检查 |

人工评审五条见 `docs/quality.md`。

## 后果

**正面**

- "质量"变成 CI 上的红绿，而不是评审者的品味；
- 体积与依赖有硬上限，防止悄悄膨胀。

**负面**

- 行数门禁会诱发"为凑行数而拆文件"，需要用"单文件 < 300 行"配合；
- 零依赖会限制某些功能（如高性能分词），需要 ADR 才能突破。

**豁免流程**

违反任一门禁必须在 `docs/adr/` 新增一条 ADR 说明理由与回滚方式；没有 ADR 的豁免一律视为回归。
