# ADR 0025：可选模型能力的注入方式

- 状态：Accepted
- 日期：2026-10-29
- 关联：ADR 0015（affect 分析器端口）、ADR 0024（适配层归属）

## 背景

affect 分析器早已是构造注入（`SoulOptions.analyzer`）。加 LLM 蒸馏时，我一度把它做成
每次调用传参（`observe(turn, { llm })`），于是同一个类里出现两套接线方式。多个适配器
接入时，这会迫使每个适配器记住"哪个能力用哪种方式传"。

同时暴露出一个宿主差异：DSH 的账号型 provider **只在真实轮次内接受调用**，启动阶段被
`ACCOUNT_SIGN_IN_REQUIRED` 拒绝。适配器因此有额外的义务，必须写清楚。

## 决定

### 1. 所有模型能力都走构造注入

```ts
new Soul({ store, soulId, userId, analyzer?, llm?, llmMaxChars? })
```

- `analyzer`：输入侧情感分析
- `llm`：记忆蒸馏（`observe` 规则没抽到时补漏、`reflect` 提炼）
- 一个 Soul 实例 = 一次接线，所有动词共享

**不做**每次调用传参：没有"同一次会话用两个模型"的用例，多一条路径只会多一种接错的方式。

### 2. core 与适配器的分工

| 归属 | 内容 |
|---|---|
| core | prompt、JSON 契约、`null` 语义、失败回退、长度门槛 |
| 适配器 | 传输（HTTP / 进程内服务 / 子进程）、**超时**、**鉴权上下文**、重试 |

`LlmFn = (prompt) => Promise<string> | string` 是唯一契约。适配器抛错时，core 回退到规则，
不重试、不阻塞调用方。

### 3. 没有模型也必须能跑

`llm` 缺省时行为完全一致（仅规则）。有专门的测试固定这条：不注入模型时 `observe`
的返回值与注入失败时相同。

### 4. 宿主差异写进适配器文档

| 宿主 | 模型来源 | 约束 |
|---|---|---|
| DSH | `ctx.llm.stream` | **只能在真实轮次内调用**；启动时被账号 provider 拒绝 |
| CLI / 其他 | OpenAI 兼容端点 | 需要显式配置 url/model/key |
| 无模型宿主 | 不注入 | 仅规则，功能完整 |

## 后果

**正面**

- 一种接线方式，新适配器只需实现一个函数
- core 可以在没有模型的宿主上完整运行
- 宿主限制被记录，而不是靠试错发现

**负面**

- 每次调用都用一个模型（无法按动词切换）——当前没有这个需求，出现时再加显式选项
- 适配器必须自己管超时；core 不设超时（否则会与宿主的取消机制打架）
