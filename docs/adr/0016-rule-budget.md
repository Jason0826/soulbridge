# ADR 0016：规则预算与反过拟合

- 状态：Accepted
- 日期：2026-10-28
- 关联：ADR 0015

## 背景

这类系统最常见的死法：每来一个失败案例加一条规则，最后规则集只拟合了测试集。前身的 `implies_action` 就是例证——8 天触发 18 次、全是误报，最后整条删除。

## 决定（四条约束，写死）

### 1. 规则预算

- `RULES` 数组 ≤ **8** 条；种子词 ≤ **120**
- 增一条必须删一条（零和），或证明被删的那条消融贡献最低
- T17 在 CI 里断言

### 2. 禁写窄规则

只允许五种形态：

```
词类（lexicon 命中）/ 否定词窗口 / 程度词窗口 / 标点类 / 重复字符
```

**禁止**：匹配整句、匹配三字以上固定短语、为单条 golden case 打补丁、把测试集原句当词条。

### 3. dev / holdout 切分

- 40 条 dev（可看）+ 20 条 holdout（封存，只在验收时跑）
- 两者基础桶准确率差距 > **10 点** → 判过拟合，**禁止继续加规则**

### 4. 消融

每条规则在 `spec/affect.v0.md` 里给出"有它 / 去掉它"的差值；贡献 ≈0 的规则删除。

### 停写触发

> 规则达 8 条且 holdout 基础桶 < 90% → 停止扩充规则，转为 ADR 0015 的模型适配器评估。
> 规则达 8 条且 holdout ≥ 90% → 冻结规则集，任何新增需修订本 ADR。

## 后果

**正面**

- 规则集有硬上限，不会无声膨胀
- 过拟合有可量化的闸门（T16）
- "上模型"成为一条既定路径，而不是临时妥协

**负面**

- 遇到新案例时，"改规则"不再是最省事的反应——这是刻意的
- holdout 由作者编写，只能防"边改边看"，真正的检验要等 P3 真实转写

## 现状（v0.4）

| 项 | 值 |
|---|---|
| 规则数 | 8（R1–R8） |
| 种子词 | 约 90 |
| dev 基础桶 | 100% |
| holdout 基础桶 | 100% |
| 差距 | 0 点 |
