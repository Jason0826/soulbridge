# ADR 0027：代码能力与模型能力的边界

- 状态：Accepted
- 日期：2026-11-01
- 关联：[thesis](../thesis.md)（选择型记忆）、[0007 检索](../briefs/0007-retrieval-scoring.md)、[0013 事件模型](../briefs/0013-event-model.md)、[0014 轮与步骤](../briefs/0014-turn-steps.md)、[model.v0](../spec/model.v0.md)

## 背景

设计过程中反复出现同一种偏差：**为了让代码能查、能算，把语义压进 schema。**

三次实例：

| 实例 | 当时的动机 | 问题 |
|---|---|---|
| `kind` 枚举 | 代码要按类型分支 | 世界上的事有成千上万种，枚举永远不够（DuEE 就有 65 类、121 个角色） |
| `importance` 预打分 | 排序要一个数 | "重不重要"要理解内容才能判断，写死就再也改不掉 |
| `vividness` | 遗忘曲线需要一个系数 | 从不变化，等于常量 |

共同点：**把"理解"这一步提前到写入时，用代码固化。**

## 原则

> **语义归模型，结构归代码。**
>
> 代码负责**保真、可寻、可裁**；模型负责**理解、归纳、判断**。
> 任何"要理解含义才算得出"的值，不进 schema。

## 判定测试（三问）

一个值该由谁来算，按顺序问：

1. **它需要理解内容才能得出吗？** 是 → 模型
2. **它会随语境/时间/模型能力变化吗？** 是 → 模型
3. **算错的代价是"查不到"还是"理解错"？** 前者交给代码兜（索引、重试），后者交给模型兜（可重算）

三问里任一命中"模型"，就不该落成列。

## 分工表

| 能力 | 代码 | 模型 |
|---|---|---|
| 保真存储：原文、时间、来源、实体、槽位 | ✅ | |
| 检索：词面、时间窗、实体过滤 | ✅ | |
| 裁剪：条数、字符、上下文预算 | ✅ | |
| 解释：这条算什么事、什么类型 | | ✅ |
| 归纳：这个人什么样、什么教训 | | ✅ |
| 聚合：讨论过几次、多久没提、谁最常出现 | | ✅ |
| 判断：重不重要、该不该说 | | ✅ |
| 存 `confidence`/`source` 字段 | ✅ | |
| 给出 `confidence`/`source` 的值 | | ✅ |

**代码的三件事都是工程约束（可用性、成本），不是理解。**

## 由此做的删除

| 删除 | 理由 |
|---|---|
| `importance` | 预判断"重不重要" |
| `kind` 枚举 | 预分类"这算什么" |
| `vividness` | 派生值，恒定 |

保留 `type_name`：**自由文本**，用于显示与检索，代码不分支。

## 后果

**正面**

- schema 小、稳定；语义升级不需要迁移
- 换更强的模型，能力直接提升（不需要改表）
- 少一类 bug：预计算写错，永久错

**负面**

- 每次回答都要把原料给足：检索要全，否则模型无从归纳
- token 成本上升，需要裁剪策略
- 需要可复现的评测，否则"模型算"会变成"模型瞎猜"

## 2026-11-03 补充：怎么让这条边界真的被执行

只看文档，这条边界被越过三次，而且每次听起来都"合理"：

| 越界 | 当时的理由 |
|---|---|
| 槽位值"不是数字 ⇒ 实体名" | 早期没有已声明实体清单，总得决定点什么 |
| `ensureEntity(name, type = 'person')` | 模型有时不写类型 |
| `holder` 里既有 `world`/`self` 又有实体 id | 需要知道事实在谁那里 |

三次都是**代码替模型做了决定**，而每一次都以"闸门会兜底"收场——兜底让错误不再暴露，于是根因留下来。

所以边界不能只写在文档里，要写成机器能查的不变量：

```
1. 值域只在一处声明（config/domains.ts 与 config/status.ts），别处只引用
2. 语义字段不得有默认值——默认值就是一个决定
3. 语法不推语义：槽位值只有带 @ 才是实体引用
4. 库里的值必须落在值域内（历史数据只报警，不判死）
```

前三条由 `health-check` 第 9.5 节执行，第三条同时由 `test/boundary.test.ts` 的行为断言固定。
第四条只报 WARN：它暴露的是历史脏数据，不是代码错误，两类信号不能混在一起。

新增任何语义字段时，同时做三件事：登记进 `docs/declarations.json`、在 `config/` 里声明值域、在 `boundary.test.ts` 里加一条"没有显式标记就不产生语义对象"的断言。


## 需要验证

1. 同一批问题，"代码聚合"与"模型聚合"的一致率——不一致时谁对
2. 给模型的原料条数 vs 正确率的曲线（找到裁剪点）
3. 去掉 `importance` 后，排序质量是否退化（用现有 top-5 重合做对照）
