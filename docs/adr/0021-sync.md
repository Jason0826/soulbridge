# ADR 0021：跨设备同步

- 状态：Accepted
- 日期：2026-10-28
- 关联：ADR 0020（存储）

## 背景

跨设备是"跨工具"的自然延伸，但它与"本地优先"直接冲突。必须明确取舍，否则会变成"悄悄上云"。

## 三种方案

| 方案 | 隐私 | 成本 | 冲突 | 结论 |
|---|---|---|---|---|
| **我们做云 SaaS** | 数据必须出机 | 服务器 + 运营 + 合规 | 服务端串行 | ❌ 不做 |
| **同步盘 / Git + 分片文件** | 明文出机（是否加密由用户决定） | 0 | 客户端 LWW | ✅ v0.5 推荐 |
| **自建 HTTP（`soulbridge serve`）** | 用户自己控制 | 一台常开的机器 | 服务端串行 | 🔜 v0.6 可选 |

**红线**：绝不把 `soul.db` 放进 iCloud / Dropbox / OneDrive。SQLite 的 WAL 与页级写入在同步盘上会损坏——这不是概率问题，是机制问题。

## 决定

1. **R2 只改数据模型**（可合并），不实现同步
2. **v0.5 实现分片 JSONL + 任选传输**（同步盘 / Git / 手动）
3. **不做云 SaaS**；v0.6 可选自建 HTTP
4. v0 不做端到端加密（需要密钥管理，属 v1+）

## 可合并的数据模型（R2 已落地）

| 字段 | 作用 |
|---|---|
| `updatedAt` | LWW 依据 |
| `deletedAt` | 墓碑，删除不物理执行 |
| `deviceId` | 决胜时的确定性 tie-break |

合并规则：**按 id 取并集 → 同 id 取 `updatedAt` 大者 → 相等取 `deviceId` 字典序**（`storage/merge.ts`，T28/T29 覆盖）。

## 交换格式（v0.5）

```
<soulbridge-sync>/
  devices/<deviceId>/
    memories-0001.jsonl
    affect-0001.jsonl
  state/<deviceId>.json      # 已导入各 peer 的游标
```

- 每条记录 `{id, device, at, updatedAt, deleted?, ...payload}`
- 分片 ≤1000 条，追加写；写完不再修改（append-only 才可安全合并）
- 幂等：同一份分片导入两次结果不变

## 隐私

- 同步盘 = **明文出机**；除非自建（Syncthing 点对点）或使用盘商加密
- README 与 `spec/sync.v0.md` 必须写明：**默认不出机，出机由你决定**

## 后果

**正面**

- R2 不引入同步复杂度，但数据形状已就绪，未来不需要破坏性迁移
- 用户可以用零成本的方式（同步盘）实现多设备

**负面**

- LWW 会丢并发编辑（记忆以追加为主，冲突极少；情绪是弱信号，可接受）
- 不使用同步盘的用户只能手动 export/import

**测试**：T28 合并语义、T29 墓碑不复活、T26 导出导入幂等。
