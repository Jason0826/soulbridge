# ADR 0028：存储与召回都不绑定实现

- 状态：Accepted
- 日期：2026-11-01
- 关联：[ADR 0027](0027-code-vs-model-boundary.md)（语义归模型）、[model.v0](../spec/model.v0.md)、[eval-boundary-0027](../eval-boundary-0027.md)

## 背景

设计表时被问到两个问题：

1. 这套表是不是只适合 SQLite？
2. 选了 SQLite，是不是把召回也固定了？

两个问题的共同来源：**把实现细节当成了契约。** 表描述的是"关系"，SQLite 只是它的一种落地；召回描述的是"取哪些行"，BM25 只是其中一种取法。

## 决定一：存储不进入模型

**真源用 SQLite（Node 内置 `node:sqlite`），契约用 JSONL 导出。**

理由：

| 理由 | 说明 |
|---|---|
| 零依赖 | `node:sqlite` 是 Node 内置，符合 core 无运行时依赖 |
| 可携带 | 一个 `.db` 就是整个 soul；导出后能进任何系统 |
| n-ary 已解决 | `fact_slots` 摊平多值槽，不需要图库 |
| 排序不落库 | 打分在代码里，换 FTS5/embedding 不动表 |

**四条判据（任一条不成立，说明抽象错了）：**

1. 换存储要改 `entities/facts/slots/gaps` 的定义 → 错
2. 某个值只能靠 SQL 函数算出来 → 该值不该落库（ADR 0027）
3. 导出再导入后行为不一致 → 契约有问题
4. 业务代码直接写 SQL → 必须走 `SoulStore`

现在：第 1、2、4 条成立；**第 3 条未测**（导出/导入还没实现），列为验收项。

**不采用**：图数据库（要服务、n-ary 已被槽位解决）、RDF 三元组（中文检索工具差、仍要 reify）、嵌入式 KV（查询全自己建）、向量库（只能当索引，不能当真源）。

## 决定二：召回是取数原语，不是单一评分函数

**召回 = 一组按需选择的过滤方式；只有"相关式"需要打分。**

| 原语 | 取法 | 回答什么 | 打分 | 现状 |
|---|---|---|---|---|
| 实体式 | 按实体过滤 → 时间排 | 她最近怎么样 | 否 | ❌ 依赖 entities |
| 穷举式 | 按子串/时间窗过滤 → 全给 | 讨论过几次 | 否 | ✅ `findTurns` |
| 边界式 | 按会话取首尾 | 上次聊到哪 | 否 | ✅ `sessions/handoff` |
| 时间式 | 时间窗 + 状态 | 上周发生了什么 | 否 | ❌ 依赖 facts |
| 缺口式 | 未闭合 gaps 按张力排 | 该问什么 | 否 | ❌ 依赖 gaps |
| 相关式 | 打分 → top-k | 这个话题说过什么 | **是** | ✅ BM25 |

**关键**：现在的实现每轮只走"相关式"，所以"她最近怎么样"和"我们讨论过的方案"走同一条路，结果都不对。**不是排序不准，是走错了路。**

代码负责：每条原语都能筛全、筛准、能报告不完整（`truncated`）。
模型（或极小规划器）负责：选哪条原语。

## 后果

**正面**

- 换存储、换排序算法都不动模型定义
- 不同问题走不同取数方式，不再用一把尺子量所有问题
- 每条原语可单独测试、单独度量

**负面**

- 多一层选择：选错原语，结果就错（需要可观测：trace 记选了哪条）
- 原语多了以后要防止爆炸（新原语必须有明确的问题点名）
- 导出契约要维护版本

## 验收

```
1. 导出 → 导入 → 行数与内容一致，行为不变（待做）
2. 每条原语有单测：筛全、截断标记、时间/实体过滤（部分已有）
3. trace 记录"这一轮选了哪条原语"，可回放（待做）
```

## 不做的

- 不把 BM25 写进表（它是可替换实现）
- 不引入第二个真源（"真相只有一个"，索引可以重建）
- 不为"未来可能的查询"预建索引（有消费者再加）
