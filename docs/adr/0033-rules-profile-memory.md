# ADR 0033：规则 / 画像 / 记忆三层，锚点退场

- 状态：Accepted
- 日期：2026-11-02
- 关联：[ADR 0032](0032-two-layers-of-memory.md)（世界/人物两层）、[0018](../briefs/0018-behaviour-influence.md)（行为影响）、[ADR 0031](0031-model-dependency-acceptance.md)

> **2026-11-07 修订注（0018 §九 3 第二刀 A）**：分类不止决定「去哪一层」，也决定「能不能用」。
> 写入侧：`role=lesson` 一律 `candidate`（`角色=lesson` 与 `原则候选=是` 是同一条决定的两说法，
> 以前只有后者进候选队列，前者落 `active` 被当资料注入、永不被分类）；分类侧：`markRule`/`markProfile`
> 把候选置 `active`（此前队列跑完、规则仍是候选，而 `rules()` 只读 active → 规则永不触发）。
> 存量行由 schema v16 按新口径追一遍：`role='lesson' AND status='active'` → `candidate`，幂等；
> 已被分类的行角色已是 rule/profile，不受影响。
>
> 迁移第 4 条（「分类不出来的，留在记忆层当普通事实（不注入）」）由此第一次真正成立：`待修` 就是
> `candidate`，`<memories>` 不再从教训池自动捞背景文本——代价是知识型教训在分类前不出现在注入里，
> 它是设计选择，不是遗漏。

## 背景

锚点（anchors）现在的做法是：把 `结论 / 教训 / 原则 / 性格` 放在一个池子里，按置信度取前 3 条注入。

实测：

```
候选 128 条 → 注入 3 条 → 丢弃 96 条
```

把 3 改成 5 不解决问题。**根因是这个池子里混着三种性质完全不同的东西**：

| 种类 | 例子 | 正确的活法 |
|---|---|---|
| **规则**（约束行为） | "改 JSON 用 edit 工具" | 只在触发时出现 |
| **画像**（关于你） | "你要机制不要 hope" | 合并后少量常驻 |
| **记忆**（发生的事） | "上次和 a 吃火锅" | 按需检索 |

它们用同一个分数抢同一个位置——**这是用排名解决归类问题。**

## 决策

**"锚点"这个概念取消**，改为三层，各自有各自的入口和预算：

```
① 规则层   facts(type_name=规则)    触发时注入
② 画像层   合并后的判断（≤8 条）     每轮常驻
③ 记忆层   facts / conclusions      相关度 × 衰减 × 练习，按预算
```

### 1. 规则层

一条规则就是一个 fact：

```
type_name = 规则
statement = 用 edit 工具改 JSON，不要用字符串替换
slots:
  触发  = {"any":["json","package.json","版本"], "regex":"\\.json\\b", "state":"long-session"}
  动作  = 用 edit 工具或 BOM 安全写入
  作用域 = 全局 | 项目
证据    = 哪一轮被纠正过
```

**触发条件用槽位存结构化 JSON**，因为一条规则可能同时被内容与状态命中，而槽位不需要改表。

### 2. 触发规格

触发在 `agent/pre-step` 求值——**只有那里能同时拿到"这句话"和"会话状态"**。

| 触发类型 | 判据 | 例子 |
|---|---|---|
| 内容 | `any` 关键词 / `regex` 正则命中用户消息 | 消息含 `package.json` |
| 状态 | 代码维护的计数器 | 连续两轮空回复、会话 > 100 轮 |

匹配是**纯函数**，可以单测：

```ts
function fires(rule, text, state): boolean
```

- 几百条规则跑一遍正则，开销可忽略。
- 误触发最多多注入一句（代价低）；漏触发才是问题（代价高），所以**每次触发都要记日志**。

注入格式（放在注入块最后，明确是要求而不是资料）：

```xml
<rules fired="改 JSON">
- 用 edit 工具或 BOM 安全写入，不要用字符串替换
</rules>
```

**不做工具级拦截**：pre-step 拿不到"接下来要调什么工具"。第一版只做注入 + 事后核对。

### 3. 遵守率（不可省略）

`session/event` 里有 `tool/call`，插件能观察工具名与参数：

```
规则触发   → trace { event: 'rule_fired', rule }
工具违规   → trace { event: 'rule_violated', rule }
遵守率     = 1 - 违规次数 / 触发次数
```

**没有这个数，规则层就只是一个 hope**（ADR 0031 的四件套要求）。

### 4. 画像层

从结论合并而来，**每轮常驻、体积固定**：

```
≤ 8 条，每条一句
重建时机：结论新增 ≥5 条，或每周一次
来源：conclusions（带证据）
```

画像不是"更多记忆"，是**归纳的归纳**：128 条教训 → 5–8 条判断 + 一批带触发的规则。

#### 4.1 合并按维度切开（结构，不是提示词）

一条合并调用同时看所有维度，模型会把不相干的判断焊成一句（实测："以目的实现为准，大胆假设、小心求证"）。**"哪些判断属于同一维度"是语义判断，但"批次不许跨维度"是结构**，所以由代码切：

```
排队项带 dimension（写判断时定，seed 从 维度 槽读）
→ groupProfileCandidates() 按维度分组，最大的组先跑
→ 每次合并只喂一个维度，提示词里带 <scope>，输出再按维度校验
→ 没标注维度的一组不合并（要合并就得先猜维度＝编造），只报数量
```

| 判据 | 值 |
|---|---|
| 可合并 | 同一维度 ≥2 条 |
| 不可合并 | 跨维度、单条、未标注 |
| 反悔 | 合并前 trace 记 `dimension` 与 `sources`，可回放 |

#### 4.2 维度在分类那一刻落槽，队列也在那一刻喂

分类是**唯一知道"这条判断属于哪一维"的时刻**，所以维度写在 `markProfile` 里，排队也在这里：

```
新教训 → 分类（规则 / 画像 / 待修）→ 画像: id | 维度=工作方式
                                      ↓
                            写「维度」槽 + 进合并队列
                                      ↓
                    合并按维度切批（4.1）→ 画像注入
```

在此之前，合并队列**只有手工脚本在喂**：所以"画像在维护"只在有人记得跑脚本的那天成立。
现在队列由分类喂。**分类队列自己仍然靠抽取/脚本喂，这一段还没接上**，别把三步当两步。

维度定义只写一份（`PROFILE_DIMENSIONS_BLOCK`），分类提示词和合并提示词都渲染它：两份定义第一次改动就会漂。

#### 4.3 派生＝引用了来源
"合并过的行"曾经由**一个写入点打标记**来识别。别的路径写出来的行因此被当成原创，再次合并 → 压缩的压缩，越合越薄。现在判据是**内容**：

```
有 来源 槽（或旧的 合并 槽）＝ 派生行 → 永远不进合并输入
```

实测：9 条活跃画像里 8 条引用了来源，按旧判据它们全在合并队列里；按新判据只剩 1 条原创。

### 5. 记忆层

维持现状（0020）：主体优先路由、相关度 × 幂律衰减 × 练习、按预算注入。

## 迁移（128 条旧教训）

```
1. 分类：规则（有触发场景）还是画像（关于这个人）
2. 规则：抽出 触发 + 动作
3. 画像：合并成 ≤8 条
4. 分类不出来的，留在记忆层当普通事实（不注入）
```

分类用一次批量模型调用完成，**不是逐条**。

## 后果

| 影响面 | 变化 |
|---|---|
| 注入 | 从"一个 `<memories>` 池子"改为三个入口：`<rules>` / `<profile>` / `<memories>` |
| context() | 不再按 maxItems 抢位置；规则按触发、画像常驻、记忆按预算 |
| 存储 | 规则/画像仍是 facts，不建新表 |
| 观测 | `rule_fired` / `rule_violated` 进 trace，遵守率可算 |

## 验收

| # | 用例 | 期望 |
|---|---|---|
| 1 | 说"把 package.json 的版本号改了" | 注入 `<rules>`，含 BOM 规则；我确实用了 edit |
| 2 | 说"今天天气不错" | 不注入任何规则 |
| 3 | 画像层 | 每轮常驻，条数 ≤8，体积稳定 |
| 4 | 遵守率 | 能从 trace 算出，且 ≥90% |

**第 2 条防的是"规则变成墙纸"**——永远挂着的规则，模型会钝化。

## 开放问题

| 问题 | 现状 |
|---|---|
| 规则之间的冲突（两条都说"用 X"） | 先按置信度取前者，记日志 |
| 规则的作用域（项目级会不会过期） | 先存字符串，不实现 |
| 触发条件谁来写 | 第一版：模型在抽取时顺带写；旧规则批量补 |
