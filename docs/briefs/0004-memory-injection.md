# 需求说明：记忆注入的容量与触发

- 状态：Draft
- 日期：2026-10-29
- 关联：ADR 0025（模型能力）、路线图 N1（工具）

---

## 1. 一句话目的

让记忆**可以长期累积**，同时保证每轮都记得住"最重要的几条"和"和当前话题相关的几条"，
而不是固定塞同一个 5 条。

## 2. 现状与问题

现在插件每轮注入：

```js
{ types: ['strategy','fact','trait'], minImportance: 6, maxItems: 5 }
```

问题：

1. **和当前话题无关**。用户在调 UI，注入的可能是"发布窗口""数据库是 SQLite"。
2. **容量硬上限**。库里 9 条 strategy，注入 5 条——被挤出的是哪条没人知道。
   实测：用户最早立的"改动前先解释"已被新记的策略挤出。
3. **越用越糟**。记忆越多，被随机挤掉的关键规则越多。

## 3. 消费者与决定

| 消费者 | 什么时候 | 要做什么决定 | 需要什么信息 |
|---|---|---|---|
| 注入构建器 | 每次组装 prompt | 这一轮该让模型看见哪些记忆 | 锚点 + 与当前消息相关的 |
| 模型 | 任务中途 | 要不要查更多 | `soul_recall` 是否可用 |
| 用户 | 事后 | 为什么这条没被想起来 | 注入记录 `used` |

## 4. 需求

| 级别 | 需求 | 验收方式 |
|---|---|---|
| **必须** | 注入分两层：锚点（无条件）+ 相关（按当前用户消息检索） | 两条消息话题不同 → 注入的记忆不同 |
| **必须** | 锚点层有独立小预算（例如 3 条），不被相关层挤占 | 单测：锚点条数固定 |
| **必须** | 记忆总量不设上限，只限制"每轮注入量" | 写入 50 条后仍正常工作 |
| **应该** | 相关层用当前用户消息作为 query | 单测：传给 `context({query})` |
| **应该** | `used` 能区分锚点与相关 | 注入记录带来源 |
| **不做** | 一次注入全部记忆 | —— |
| **不做** | 用模型判断相关性（v0 用关键词评分） | —— |

## 5. 非目标

- 不做向量检索
- 不改变单条记忆的抽取质量（那是 0003）
- 不做跨会话的记忆淘汰策略

## 6. 成功判据（可执行）

```bash
# 1. 话题不同 → 注入不同
soulbridge context --query "数据库"    # 出现 数据库使用 SQLite
soulbridge context --query "UI 样式"   # 不出现数据库，出现其他相关条

# 2. 锚点稳定
重复多次：锚点层始终是同样几条（importance 最高）

# 3. 容量
写入 50 条记忆后，注入仍 ≤ 锚点 + 相关 的预算
```

## 7. 前置条件与时机

- 可以立即实施：插件已能拿到用户消息（`user/message` 事件），core 的
  `context({query})` 已支持查询
- 依赖：无
- 不做的情况：如果按消息排序后"相关层"经常为空（关键词不匹配），
  则退回固定 + 扩大上限，并把问题记在 0004 的观察里

## 8. 开放问题

1. 锚点怎么定？`importance ≥ 8` 还是"用户明确标记为长期"？
2. 锚点预算几条合适？3 条还是 5 条？
3. 相关层查不到时，退回什么？按重要度取前 N，还是留空？
4. 插件拿到的是**上一轮**的用户消息（`systemPrompt.section` 在组装时求值），
   时序是否可靠？需要在真实会话里验证。
