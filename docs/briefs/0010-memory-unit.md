# 需求说明：一条记忆是什么

- 状态：**Superseded（2026-11-02，→ 0014 轮与步骤 + 0017 主题线索）**
- 日期：2026-10-31
- 关联：thesis（选择 > 容量）、ADR 0003（内容记忆留端口）、ADR 0026（L0/L1）

---

## 1. 一句话目的

定义"一条记忆"的边界，让**时序、权重、选择**三件事有地方挂。

现在的记忆是抽取后的"一句话"，长度从 7 字到 18202 字不等——没有边界，下游所有判断都失真。

## 2. 现状与问题

| 问题 | 证据 |
|---|---|
| **长度无界** | 库里有 7 字的，也有 18202 字的 |
| **长文档支配召回** | 旧评分下那条 18202 字的在 **85%** 的 query 里进 top3，top1 平均 12150 字 |
| **不记交流** | 只存用户的话，不存助手的回复——伙伴感只剩一半 |
| **边界靠抽** | 抽出来是"一句结论"，回到原文就对不上 |
| **编码未处理** | 那条 18202 字里，解码后真实内容只有 2072 字，其余是 `&#x20;` 这类 HTML entity |

最后一条说明：**问题不只是"存太多"，是"存的形态不对"。**

## 3. 消费者与决定

| 消费者 | 什么时候 | 要做什么决定 | 需要什么 |
|---|---|---|---|
| 写入（observe） | 每轮 | 这一轮怎么切成条目？多长要提炼？ | 边界规则 + 长度上限 |
| 召回（pre-step） | 每轮 | 按什么单位检索？ | 统一的条目粒度 |
| 注入 | 每轮 | 取几条、要不要聚合？ | 条目可聚合 |
| 归纳（离线） | 定期 | 从哪些条目归纳出"这个人"？ | 条目带主体 |

**四个消费者的共同前提都是：条目有明确边界。** 所以这是地基，不是优化项。

## 4. 需求

| 级别 | 需求 | 验收方式 |
|---|---|---|
| **必须** | 一条记忆 = 一个交流单元（用户 + 助手），不是单句 | 单测：写入一轮后，读出的条目同时含两侧；**各阶段怎么读这个单元见 [ADR 0035](../adr/0035-stage-input-contract.md)** |
| **必须** | 每条带 `at`（时间） | 单测：条目有非空时间 |
| **必须** | 长度上限；超过则提炼，原文落冷备 | 单测：写入超长轮次后，注入侧条目低于上限 |
| **必须** | 原文不可变；派生视图可重建 | 删掉所有派生表，能从原文重建 |
| **应该** | 三轴：`type` / `subject` / `time` | 每条能回答"是什么、关于谁、何时" |
| **应该** | `metadata` 作为开放容器，未定字段先放这里 | 加字段不改 schema |
| **不做** | 预先枚举关系类型（同事/朋友/喜欢…） | —— |
| **不做** | 为"未来可能用到"预留正式列 | 没有消费者的列不进 schema |

## 6. 验证（已做）

**假设：** 检索单位用"一问一答"会不会损失精度。

**方法：** LongMemEval-S，分层抽样 120 题，同一 BM25，唯一变量是聚合粒度。

| 臂 | R@1 | R@5 | R@10 | R@20 |
|---|---|---|---|---|
| A 单轮 | 52 | 74 | 80 | 84 |
| **B 问答对** | **53** | **80** | **85** | **92** |

条目数 **496 → 250**（减半）。

**结论：假设成立。** 问答对在召回上全面更好，同时条目减半。

**同时暴露：** B 的长度 p90 = 3145、max = 78118。**长度上限不是可选项。**

复现：`_scratch/longmemeval/pair_test.py`

## 7. 没验证到的（别当成结论）

1. **三轴够不够。** 按现有使用看不出缺口，但不代表未来没有。这正是"兼容性"要解决的事——不是现在定义全，而是让定义可被推翻。
2. **长度上限取多少。** 500 字是直觉，没有实验支撑。
3. **从 turn_pair 重建画像的可行性。** 归纳那一步没测。
4. **中文场景。** 上面的验证用的是英文语料。

## 8. 兼容性原则

未来不确定，所以不追求"定义全"，追求"推翻得动"：

1. **原文不可变，视图可重建。** 只要原文在，任何新的解释都能重算；只存结论则错了就永错。
2. **开放容器优于预留列。** 未定字段先放 `metadata`，有消费者了再提成正式列。**预留列是债。**
3. **不预设枚举。** `type` 是字符串不是 enum；加新类型不改 schema。
4. **买检索，自研结构。** 检索实现会商品化（外部服务可换）；条目结构承载选择信号，不能外包。

## 10. 两个注入机制的分工（2026-10-31 重新审视）

### 现状：同池，两种过滤

| | 放什么 | 过滤条件 |
|---|---|---|
| system prompt（锚点） | 记忆条目 | `type ∈ {strategy,fact,trait}` + `importance ≥ 8` + ≤3 条 |
| pre-step（相关） | 记忆条目 | 按当前消息相关性 + ≤5 条 |

两者从**同一个池子**取**同一种东西**，只是筛法不同。后果：

- 一条 `importance ≥ 8` 又刚好相关的记忆会**同时出现在两边**
- pre-step 曾在没有匹配时仍注入 `<soul>/<style>`，与 systemPrompt 重复（2026-10-31 修，plugin 0.0.34）

根因不是某个 bug，是**两个机制没有本质分工**。

### 新分工：一个放结论，一个放原文

| | system prompt | pre-step |
|---|---|---|
| 放什么 | **画像**（归纳结论） | **交流片段**（`turn_pair`） |
| 粒度 | 一条判断 + 证据 id | 一问一答 |
| 回答的问题 | "我知道你是什么样的人" | "我想起我们聊过什么" |
| 来源 | `judgment`（从 `turn_pair` 归纳） | `turn_pair` |
| 触发 | 每轮固定 | 按当前消息检索 |
| 变化频率 | 低（要重复才更新） | 高（每轮不同） |

对应 thesis 的两件事：**选择 → 画像 → system prompt；时序 → 片段 → pre-step。**

因为一个是结论、一个是原文，**天然不重复**——现在的重复正是"两种过滤同一批数据"的症状。

### 三条具体结论

1. **锚点不该用 `importance ≥ 8` 选。** 实测 `importance` 只有 4 档、`vividness` 永不变化，用没有分辨率的字段做"最重要 3 条"，选出来的是噪声。画像天生只有 5–20 条，不需要阈值。
2. **pre-step 该召回片段，不是条目。** 条目边界不清（7 ~ 18202 字）；片段长度可控、双向、有上下文。LongMemEval 验证：R@5 片段 80 vs 单轮 74。
3. **`<style>` 现在是常量。** `bond=2.0` 已饱和，每轮注入同一句"像朋友一样聊天"，不再携带信息（B4 已知问题）。

### 前提与落地顺序

**画像和 `turn_pair` 都还不存在。** 所以本节是设计，不是可立即实现的改动。

1. `turn_pair` 落库（本文 §4）
2. 归纳产出 `judgment`（未验证，见 §7）
3. 两个机制各接一边

**在此之前不改代码**——现在改，两边取到的都是空。

### 验收

- 同一条内容不应同时出现在两个机制里
- system prompt 的内容变化频率应**远低于** pre-step
- pre-step 的每条注入能追溯到具体 `turn_pair`
