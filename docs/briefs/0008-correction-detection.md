# 需求说明：纠正检测（规则 / 结构 / LLM 三层）

- 状态：Draft
- 日期：2026-10-30
- 后续：RFC 0003（自我提炼 A/B 阶段）、ADR 0018（repeatCorrection 主指标）、`briefs/0005`（harness）
- 起因：`corrections` 表在真实使用中一直是 0 行

---

## 1. 一句话目的

让"用户纠正了"这件事**能被识别出来**，否则 `repeatCorrection`（ADR 0018 的主指标）没有分子，RFC 0003 B 阶段也永远没有输入。

## 2. 现状与问题（实测）

判定规则只有一个正则，共 7 个短语：

```js
const CORRECTION = /(不对|不是这样|错了|你搞错|wrong|that'?s not right|incorrect)/i
```

用本会话 19 条真实发言测试：

| 输入 | 结果 |
|---|---|
| 这算不算你重复犯了错 | 漏 |
| 这些 steering 不也是个人经验吗？为什么不能写进 soulbridge？ | 漏 |
| 我觉得有问题，聊项目设计也是日常使用啊… | 漏 |
| 我明明纠正过你，为什么 correction 还是 0 | 漏 |
| 我不太同意这个设计 | 漏 |
| 换个做法 | 漏 |
| 那是错的 | 漏（表里是"错**了**"，没覆盖"错**的**"） |

**真实发言 0/19 命中。** 唯一命中过的两句话是测试时人工构造的。

根因：中文纠正很少出现"错了"这类词，它出现的是**对比**——我给了判断 A，用户给了与 A 冲突的 B。这个词面信号不存在。

## 3. 消费者与决定

| 消费者 | 什么时候 | 要做什么决定 | 需要什么信息 |
|---|---|---|---|
| `corrections` 表 | 每轮 | 这条要不要记为纠正证据 | 是不是纠正 + 被纠正的是哪句回答 |
| RFC 0003 B | 会话/周期 | 是否提炼成策略 | 同类纠正是否重复出现 |
| ADR 0018 度量 | 4 周 | 同类错误有没有减少 | `repeatCorrection` 分子 |
| 用户 | 事后 | 它到底记住了哪次纠正 | 可查的纠正列表 |

## 4. 需求

| 级别 | 需求 | 验收方式 |
|---|---|---|
| **必须** | 三层判定：L1 规则（高精度）→ L2 结构信号（候选）→ L3 LLM 仲裁（仅候选） | 三层各自的召回/误报可分别测量 |
| **必须** | 分档记录结果，照抄 `llmOutcome` 的形状：`rule / structural / llm-yes / llm-no / failed` | `corrections` 能回答"为什么没记" |
| **必须** | 默认方向写死：**规则宁漏勿错，但必须有兜底** | 没有兜底的"宁漏"等于"没有" |
| **必须** | 黄金集：真实发言 + 人工标答案，每次改动跑回归 | 召回与误报两条曲线同时记录 |
| **应该** | L2 只做结构判定，不看关键词：上一轮给断言 A，本轮给出与 A 冲突的 B | 构造用例验证：不含任何否定词也能命中 |
| **应该** | L3 只对候选调用，不逐轮全量 | 记录调用次数与延迟 |
| **不做** | 自动从模型判断里学习、自动扩充词表 | 那是回声室，不是学习 |

## 5. 非目标

- 不解决"提炼成策略"（RFC 0003 B，本项只负责识别）
- 不判断"用户为什么不满意"（只判是不是纠正）
- 不做跨会话的纠正聚类

## 6. 维护与更新（这一节决定了它会不会烂掉）

三层里**只有 L3 是主要迭代点**，L1/L2 应该越用越稳定。

| 层 | 会不会更新 | 怎么更新 | 防腐烂 |
|---|---|---|---|
| **L1 规则** | 很少 | 只有当黄金集里某类**显式**纠正长期漏，且新词不会引入歧义时才加；每次加词必须带一条用例 | 规则数上限（照 affect 的 `RULE_BUDGET` ≤8）；没有正例的规则视为死代码，删 |
| **L2 结构** | 偶尔 | 发现新的**对话形状**（如"改口/转移话题"）时新增一条结构，不是加词 | 每条结构必须有 ≥2 条反例（不该命中的对话） |
| **L3 LLM** | 持续 | 提示词与判据迭代 | 每轮改动都跑黄金集；误报上升即回滚 |

判断"该往哪层加"的规则：

> 如果 L1 需要不停加词，说明判定放错了层——该下沉到 L2 或 L3。

**规则不会自己更新**，也不应该：自动扩充 = 从自己的判断里学习 = 回声室。更新路径固定为：

```
真实使用 → 黄金集新增一条失败样本 → 人工确认标准答案
        → 提出规则/结构/提示词变更 → 跑全量回归 → 合入
```

更新频率**按事件而不是按时间**：黄金集新增失败样本 ≥3 条时触发一次。

## 7. 成功判据（可执行）

```
黄金集（19 句起步，人工标答案）
  → L1 精度 100%（命中必须对）
  → L1+L2 召回 ≥ 60%（覆盖显式与结构两类）
  → L1+L2+L3 召回 ≥ 85%，误报 ≤ 10%
  → 每层单独出数，而不是只报总分

真实使用
  → corrections 行数 > 0，且连续两周不出现"用户明确说不是纠正"的误报
```

阈值在黄金集标完答案后再定稿——现在写死等于拍脑袋。

## 8. 前置条件与时机

- **什么时候可以实施**：**已纳入 S1 范围内**（2026-10-30 明确决定，见 [stages/s1-dsh-memory.md](../stages/s1-dsh-memory.md)）。理由：声明了但没实现，按 bug 处理。
- **本阶段能做到哪一层**：L1 + L2 + `correctionOutcome` 分档。**L3 LLM 仲裁推迟**——它要新增模型调用，属于新功能。
- **黄金集已就绪**：`packages/core/test/fixtures/correction-golden.ts`（19 条，人工标注，分 clear/ambiguous 三组），基线已钉死：L1 在 clear-yes 上召回 **0/6**、clear-no 误报 0、ambiguous 0/2。
- **什么情况下不做**：如果标完答案发现"真实纠正"本身就极少（比如一周 <2 次），那 `repeatCorrection` 的样本量撑不起 4 周实验，应该先解决"怎么让用户愿意纠正"这个问题。
