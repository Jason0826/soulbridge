# 需求说明：记忆的时效与取代

- 状态：Implemented（0.0.15）
- 日期：2026-10-29
- 后续：路线图 N3 → 待写 RFC 0004

---

## 1. 一句话目的

避免**同一事实的旧值和新值同时被注入**，也避免**明确过期的内容**继续影响判断。

具体场景：用户先说"发布窗口是周三"，三周后说"改成周四"。今天两条都会进 prompt，
模型可能挑错。现在 `supersededBy` / `validUntil` 字段存在但没有任何逻辑使用它们。

## 2. 消费者与决定

| 消费者 | 什么时候 | 要做什么决定 | 需要什么信息 |
|---|---|---|---|
| 注入构建器（`buildContext`） | 每次组装 prompt | 这条记忆该不该进这一轮 | 是否过期、是否已被取代 |
| 按需召回（`recall`） | 模型主动查 | 返回哪些条目 | 同上 |
| 记忆列表（`list` / `status`） | 用户检查 | 哪些是当前有效、哪些是历史 | 状态与取代链 |
| 反思（`reflect`） | 写入新记忆 | 新条目是否取代旧条目 | 与旧条目的冲突判定 |

没有消费者的是 `validFrom`：`createdAt` 已覆盖它的职责，本次不动它，后续 schema
变更时移除或明确降级为别名。

## 3. 需求

| 级别 | 需求 | 验收方式 |
|---|---|---|
| **必须** | 过期的记忆（`validUntil <= now`）不进 `context` | 单测：写入 `validUntil=now-1`，`context` 不含它 |
| **应该** | 提供**显式**取代接口（人触发），旧条目置 `status=superseded`、`supersededBy=新id`，不删除 | 单测：`supersede` 后旧条目不进 `context`，仍可 `list` |
| **必须** | 被取代的记忆仍可被 `list` 查到（历史可追溯） | 单测：`list` 返回 superseded 条目 |
| **应该** | `recall` 同样排除过期与被取代 | 单测 |
| **应该** | `status` 显示有效/被取代/过期数量 | 手工：`soulbridge status` 输出 |
| **不做** | 自动判定冲突（规则不可靠，见 RFC 0004 §3） | —— |`n| **不做** | 用模型判断"是否冲突" | —— |
| **不做** | 物理删除过期记忆 | —— |

## 4. 非目标

- 不做语义相似度判定冲突（v0 用确定性规则，见开放问题）
- 不做自动续期（"这条还没过期，续一下"）
- 不做多用户共享记忆的冲突合并

## 5. 成功判据（可执行）

```bash
npm test                        # 新增用例全绿，既有 84 条不回归
node packages/cli/src/cli.ts context   # 不出现过期/被取代条目
node packages/cli/src/cli.ts list      # superseded 条目仍在，且标注状态
```

## 6. 前置条件与时机

- 可以立即实施：schema 列已存在，无需迁移、无需模型、不依赖其他未完成项
- 依赖：无
- 不做的情况：如果"冲突判定"无法用确定性规则达到可接受精度，则只做**过期过滤**
  （必须项第 1 条），把取代留到有模型提炼的阶段

## 7. 开放问题

1. ~~冲突判定规则~~ → **已决**：v0 不做自动判定。三种确定性规则（关键词重叠 / 公共前缀 /
   实体+谓词）都有反例，误取代比不取代更糟。改为显式 `supersede`，见 RFC 0004 §3。
2. **过期记忆的处置**：仅过滤，还是同时把 `status` 置为 `archived`？（倾向：过滤，
   状态不变，避免把"过期"和"归档"混为一谈）
3. **取代链的深度**：A 被 B 取代、B 被 C 取代时，`list` 是否要能显示链条？
   （v0 只记直接前驱，不做链）
