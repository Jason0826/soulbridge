# 需求说明：模型兜底蒸馏的质量

- 状态：Resolved（根因是适配器重复拼接，插件 0.0.23 修复）
- 日期：2026-10-29
- 后续：待写 RFC

---

## 1. 一句话目的

让模型兜底能记住**长期有效的事实陈述**（例如"我们的发布窗口在每周三"），
同时继续拒绝闲聊和一次性信息。

## 2. 消费者与决定

| 消费者 | 什么时候 | 要做什么决定 | 需要什么信息 |
|---|---|---|---|
| `observe` 的模型兜底 | 规则没抽到、消息 ≤2000 字 | 这条要不要存、存成什么类型 | 提示词 + 模型的判断 |
| 用户 | 事后 | 该记的有没有被记住 | `soulbridge list` / 注入内容 |
| 维护者（我们） | 调参时 | 是改提示词还是修解析 | `llmOutcome` 分布 |

## 3. 现状数据（0.0.18 之前，日志无法区分 null 与 failed）

| 消息 | 规则 | 模型 | 备注 |
|---|---|---|---|
| `我们的发布窗口在每周三` | 漏 | `by=none`，946ms | **期望被记住**，实际没有 |
| `记住：测试工具` | 命中 | 未调用模型 | 规则吃掉，符合预期 |
| `可以，回复了` | 漏 | `by=none`，1181ms | 期望不记 |
| 3871 字粘贴 | 漏 | 未调用（超 2000 字跳过） | 符合预期 |

问题：`by=none` 把"模型说 null"和"模型答坏了"混在一起，所以**现在无法判断**
"发布窗口"那次是提示词问题还是解析问题。

### 0.0.18 之后的第一条数据（2026-10-29 16:02）

```
observe ok: chars=3 written=0 committed=false by=none llm=failed ms=2263
```

**`failed`，不是 `null`。** 2263ms 说明请求发出去了，返回内容无法解析。

### 根因（2026-10-29 16:30，原文日志）

```
"{\"type\":\"null\",\"text\":\"\"}{\"type\":\"null\",\"text\":\"\"}"
```

模型回了一份 JSON，**适配器把它拼了两份**：流里先有 `text-delta`（增量），
再有 `block-end`（整块），采集器两个都累加。两份首尾相连 → 解析必然失败。

结论：不是提示词问题，不是模型问题，是**适配器的采集 bug**。
修复见插件 0.0.23（`collectText`：只收增量，无增量时才用整块），两个测试固定。

方向修正：问题大概率不在"模型判断保守"，而在**输出格式**。因此新增一条需求——
失败时必须能看到模型的原始输出，否则调提示词就是盲改。

## 4. 需求

| 级别 | 需求 | 验收方式 |
|---|---|---|
| **必须** | 日志能区分 `llm=null` / `llm=failed` / `llm=stored` | 已实现（0.0.18），首条数据为 `failed` |`n| **必须** | 失败时保留模型的**完整原始输出**（不截断） | 单独文件 `llm-raw.log`，每条一行 |`n| **必须** | `llmOff` 不能把"没配模型"和"规则先命中"混为一谈 | `off` / `skipped-rules` / `skipped-long` 三态 |
| **必须** | 长期事实类陈述（时间/约定/配置）能被记住 | 固定样本集上 ≥80% 为 `stored` |
| **必须** | 闲聊、一次性情绪、纯礼貌语不记 | 同上样本集上 ≥90% 为 `null` |
| **应该** | 改动能被复现，不依赖"感觉变好了" | 同一批样本重跑结果可比 |
| **不做** | 为提升召回而放宽到"什么都记" | —— |
| **不做** | 在没有 `llmOutcome` 数据前改提示词 | —— |

## 5. 非目标

- 不做语义去重/近似合并（那是另一条线）
- 不改规则抽取器（`ruleExtract`）的行为
- 不引入外部模型或端点（继续用宿主模型）

## 6. 成功判据（可执行）

```bash
# 1. 日志里出现明确的三态
grep "observe ok" ~/.soulbridge/plugin.log | tail -5
# 期望：llm=null / llm=stored / llm=failed 中至少各出现一次

# 2. 固定样本（12 条，事实/偏好/闲聊/抱怨各 3 条）在真实会话里逐条发送
#    记录每条的结果，统计：
#    事实/偏好类 stored ≥ 80%
#    闲聊/抱怨类 null ≥ 90%
```

## 7. 前置条件与时机

- **可以开始的条件**：拿到重启后（0.0.21）的第一组 `llmOutcome` 数据
- **依赖**：0.0.18 的 `llmOutcome`（已发布）
- **关键约束**：DSH 的账号 provider 只在真实轮次内可用，
  **无法离线批量跑样本**——评估只能靠真实会话逐条进行，或者等一个有 API key 的端点

## 8. 开放问题

1. **评估怎么做才可复现？** 逐条发 12 句会污染真实记忆库，是否用独立 `SOULBRIDGE_HOME`？
2. 如果 `llm=failed` 占多数，是提示词太啰嗦导致模型不守格式，还是 `parseLlmJson` 太严？
3. "记住：X" 这类显式指令，规则已经命中，模型兜底不应再介入——是否需要在分流逻辑上明确？
4. 事实类的 `importance` 用多少？现在 `llmExtractTurn` 里 fact 固定 6，可能低于注入阈值。
