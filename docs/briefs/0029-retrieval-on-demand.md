# 需求说明：按需取数（先理解意图，再决定取什么）

> 由来：用户 2026-11-08 18:48 的原话——
> "真实情况应该是，用户说了一句话，你来理解用户意图，然后思考是否有教训，有规则，
> 这里是先思考用户意图，再判断去找哪些记忆，是不是可以用按需读取的方式来做呢？"
>
> 一句话：**取数权该在模型（它理解意图），不该在代码（关键词猜）。**

## 0. 通用性验收线（先放这里——能被证伪才算数）

```
阶段 1 的判决线：加目录之后，soul_recall / soul_detail 的调用次数 > 0
                  （今天基线：soul_recall 生产至今 0 次）
                 且取回的条目人工抽样 10 次里 ≥7 次相关
         不过 → "模型主动取数"这条路记失败，改用阶段 2 的探针，不硬撑
```

## 一、现状：取数权在代码，而且测得不好

匹配器就是 `packages/core/src/rules.ts` 的 `fires()`：拿用户消息做子串匹配。
把现在库里的 **188 条 active 规则**套回最近 **200 条真实用户消息**（只读回放）：

| 指标 | 数 | 含义 |
|---|---|---|
| 每条消息命中几条 | p50 **1** · p90 **7** · max **53** | 一条消息能让 53 条规则想进来 |
| 命中 0 条 | **94 / 200（47%）** | 一半消息一条规则都不响 |
| 命中 > 5（被截断） | **31 / 200（16%）** | 超预算按 confidence 砍，砍掉几条不记数 |
| 200 轮里从没命中的规则 | **72 / 188（38%）** | 含 10-28 就存在的老规则 |

触发槽本身的形状：

```
179 条用关键词（any）· 0 条用正则（regex）· 7 条用状态（state）
关键词个数：2 个 64 条 / 3 个 98 条
关键词长度：1-2 字 157 个（"教训""重启""改动"这种）
最高频词：教训×7 soulbridge×7 review×6 valid_from×6 valid_to×6
```

**结论：问题不是"正则不好"，是匹配对象错了。** 现在全部规则都在匹配"用户说了什么词"，
而规则该匹配的是"我正在做什么"（上 edit、写 .json、跑 Set-Content、重启）。

**工具早就有了，但没人用**：插件注册了 `soul_recall` / `soul_remember` / `soul_detail`
（`dsh-plugin-soulbridge/index.js`），生产调用 `soul_recall` **0 次**。
原因不是模型懒：**目录里没有"我记过哪些条目"**，它不知道有东西可查，也就没有理由查。

## 二、设计：三层，各自解决一种确定性

```
L0 目录（常驻，小）    「我记得有这些」——一句一条，中立语气，不带正文
                       写 JSON 改配置要防 BOM · fc_x
L1 正文（按需取）      看到目录里相关的 → soul_detail 取全文 + 证据 + 作用域
L2 动作触发（兜底）    「我要动手了」时匹配动作：写 .json / 跑 Set-Content / 重启
```

| 层 | 谁判断 | 何时 | 失败模式 | 成本 |
|---|---|---|---|---|
| L0 目录 | 代码（全量、不做判断） | 每轮固定 | 不做判断，就不会判断错 | 20 条 × 30 字 ≈ 300 token/轮 |
| L1 取正文 | **模型**（读懂了意图） | 它觉得需要时 | 模型不取（**可观测**：调用次数） | 一次工具往返 |
| L2 动作 | 代码（结构判定） | 动手前 | 漏配动作类型 | 无模型成本 |

三层分别修掉第一节的三个数：

```
47% 零命中      → 目录不依赖措辞，永远有内容可看
16% 被截断      → 不再按 confidence 砍 5 条，只有真被要的才取
72 条从不命中   → 按作用域与复现频率分层，弱的降到 L1（被问才出现）
```

## 三、为什么不一步到位改成纯拉取

失败模式不对称，而我们**已经测到过一次**：

```
关键词推送   失败 = 多注入几条噪声（浪费注意力，答案还在）
纯拉取       失败 = 该用的记忆一条没来（用户不知道它错在哪）
模型主动调用 已测：0 次
```

所以顺序是：**先给目录（让它有理由主动）+ 关键词推送保留作兜底与对照**，
用调用次数决定下一步，而不是靠设计者觉得哪种更优雅。

## 四、数据模型要加的东西

目录不是把 `statement` 截短就行——**每条规则需要两个表示**：

```
现在   规则 = 一整句祈使句（既当索引又当正文）
需要   索引句  ≤30 字、中性（"改 JSON 的配置要防 BOM"）   ← 常驻 L0
       正文    完整做法 + 触发证据 + 作用域 + 怎么学到的  ← 按需 L1
```

这条判据用户早给过（记忆 `fc_mvyz1jx8_2`）：**每条记忆先存一句话事实，先想到有这件事，再展开细节。**
库里现在没有这个字段，规则只有 `statement` + `触发`。

索引句的产出口径（不新增模型调用）：分类器输出多一列 `索引=…`；
存量 188 条一次性补齐（约 19 批，走 `pending-classify` 自己的写者，不新开写路径）。

索引条目还要带 **scope + 复现频率**（用户既有规则：教训按作用域与复现频率衰减，
不能一律常驻），否则 L0 迟早又变成 188 行的墙纸。

## 五、三个阶段与各自的判决

```
阶段 1  分类器多产「索引句」→ pre-step 渲染 L0 目录（≤20 条）→ 关键词推送保留
        观察 3 天：soul_recall / soul_detail 调用次数、注入块大小、推送命中率
        判决：调用次数 >0 且抽样相关率 ≥70% → 进阶段 2；仍为 0 → 直接进阶段 2

阶段 2  意图探针：一次小模型调用，输入 = 用户消息 + 目录，输出 = 要取的 id（≤5）
        与关键词推送 A/B 对比：零命中率、截断率、注入条数、相关率
        判决：探针的相关率显著高于关键词（同一批历史消息回放）→ 推广

阶段 3  话题类规则从推送降级为按需；推送只保留动作类（L2）
```

## 六、成本口径（按今天的实测换算）

```
L0 目录   20 条 ≈ 300 token/轮，命中缓存约 ¥0.00001/轮
探针      ≈ 1.5k token/轮（消息 + 目录 → id 列表）≈ ¥0.002/轮（离峰）
对照      当前每轮 ¥0.23（203k 上下文），注入块本身 9.5k 字符
```

结论：**按需取数不是省钱手段，是质量手段**——它换掉的是"猜错"（47% 零命中、16% 盲砍），
不是上下文长度。省钱靠的是开销不变时少注入噪声。

## 七、不做什么

1. **不做向量检索**：没有 embedding 基础设施，先不上；语义判断交给模型，不引入第二个检索器。
2. **不删关键词推送**（阶段 1）：它是对照组，也是兜底。
3. **不把目录当指令**：目录是"我记得有这条"，不是"你必须这么做"——
   两者混在一起，就又变成墙纸（ADR 0033 的原话）。
4. **不新增第二条写路径**：补索引句走分类队列自己的写者。

## 八、开放问题

1. 目录放多少条？20 / 50 / 全量 188（≈3.5k token，缓存后便宜但占注意力）。
2. 存量 188 条补索引句要不要现在花 19 批模型调用（每批 10 条）。
3. L2 动作触发需要"动手前"的钩子：插件当前只挂 `agent/pre-step` 与 `session/event`，
   要先确认 DSH 有没有工具级中间件（`agent/pre-step` 拿到的是本轮起始状态，看不到即将发生的 `tool/call`）。
4. 目录的排序：作用域（全局 > 项目）× 复现频率 × 后果强度 —— 需要一个能算的数，
   否则又是 confidence 那种"和当下无关"的排序。

## 九、索引句的验收线：带信息，不是指路（2026-11-08 补）

L0 的目录句是模型看见记忆的**唯一接口**，所以它自己要先通过验收。用户抽读 20 条
（超长 7 条 + 确定性随机 13 条）判 ✗ 5 条，病型只有两类：

- **写了位置**：「重启杀掉 turn 18」「抽取生效以 unit=Nturns 日志为准」——未来的我看不到那个位置。
- **写了动作**：「抽取模板加了「有效到」字段」——记的是改动，不是改动之后定下来的规则。
  另有一条是口号（「人物实体要查文献，不靠猜测」），没有信息只有态度。

抽样 25% 的坏率，而形态检查（turn 编号 / id / commit / 日志标记 / 变更记录）只能抓到
4%（7/189）——**差距说明剩下的病灶是语义的**，因此：

1. 索引句的定义收成一处（`INDEX_LINE_RULES`），分类批次与索引批次共用，附三条禁令：
   不写位置、不写变更、离开原句能读懂。
2. 存量全量重写一次（同一条队列、同一个提示词，reason=`索引重写`，桶排最后），
   一次性 marker：新提示词覆盖此后所有新规则，再跑只会把好的改一遍。
3. 形态闸门拦住本地坐标与变更记录，**不写库、保留旧行、计 `index-rejected`**——
   宁可留一条旧的可读行，也不覆盖成更差的指针。语义病仍由人的抽样判。

验收：重写后再抽 20 条，若 ✗ 仍 ≥4 条，说明问题不在写法而在分类器理解不了原句，
那时要回头改的是索引句的**来源**（谁写、看着什么写），不是再加禁令。
