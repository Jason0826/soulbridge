# 需求说明：检索漏斗与上下文预算（0020）

- 状态：Draft
- 日期：2026-11-02
- 关联：[ADR 0028](../adr/0028-storage-and-recall.md)（取数原语）、[0019 记忆选择与遗忘](./0019-memory-selection.md)、[0017 主题线索](./0017-topic-threads.md)
- 由来：0019 定完"全部保留、衰减的是召回概率"之后，问题从"删不删"变成"怎么在有限窗口里取出来"；以及一个实测错误——"上次和 a 吃饭"被答成了"上次闭合的线索"

---

## 1. 问题

0019 确定：**原文全留，衰减的是被想起的概率。** 于是稀缺的不再是磁盘，而是：

```
① 上下文窗口（一次只能放几千 token）
② 注意力（放进去越多，模型越分不清哪个重要）
```

所以检索层要回答三件事：

1. **取哪一层**（原文 / 钩子 / 章 / 画像）
2. **用哪个原语**（实体 / 时间 / 线索 / 文本 / 缺口）
3. **花多少预算**（各层条数与字符上限）

## 2. 一个实测错误：把"上次"当成了原语

| 问句 | 现在的行为 | 正确行为 |
|---|---|---|
| 上次和 a 吃饭 | 返回**上一闭合线索**（可能是聊 b 的） | 返回 a 的时间轴里最新的"吃饭" |
| 上次和 c 吃饭 | 同上 | a 没有就诚实说没有 |
| 上次聊到哪 | 上一闭合线索 ✅ | 不变 |

**根因**："上次"不是取数方式，是**修饰词**。它必须和"关于谁/什么"绑定，绑谁就取谁。

所以问句要拆成四个槽位：

```
主体    关于谁 / 什么（实体，或"这段对话本身"）
谓词    做什么（吃饭、吵架、重构）
时间    上次 / 上周 / 某天
意图    想知道什么（陈述、确认、追问细节）
```

**"上次"只影响排序方向（倒序取最近），不决定取什么。**

## 3. 原语表（在 ADR 0028 六种之上补两条）

| 原语 | 输入 | 返回 | 回答什么 | 打分 |
|---|---|---|---|---|
| **实体时间线** | 实体 + 谓词? + limit | facts 按时间倒序 | 上次和 a 吃饭 | 否 |
| **会话连续性** | 无（隐含"这段对话"） | 上一闭合线索 | 上次聊到哪 | 否 |
| **时间窗** | since/until | 时间窗内的 turns + facts | 上周做了什么 | 否 |
| **穷举** | 子串 / 类型 | 全部命中的 facts | 讨论过几次 | 否 |
| **缺口** | — | 未闭合 gaps 按张力 | 该问什么 | 否 |
| **相关** | 问句 | BM25 top-k | 这个话题说过什么 | **是** |

**七种里只有一种要打分。** 0019 的幂律衰减与访问强化只作用在"相关式"和"实体时间线"的排序上。

## 4. 路由：先确定性，后兜底

```
问句里出现已知实体（含别名）？
  是 → 实体时间线(实体, 谓词?)
  否
    ├─ 有"上次/刚才/继续" → 会话连续性
    ├─ 有时间词（上周/昨天/那天）→ 时间窗
    └─ 其它 → 相关式（BM25）
```

**路由是规则，不调模型**——它只做"实体名匹配"，不判断语义。认错了退化成相关式，不会答错成另一个实体。

## 5. 漏斗与预算

```
① 定向（候选 id，不注入）
② 收敛（注入钩子）
     L3 画像     ≤ 3 条
     L2 当前线索 ≤ 1 条
     L1 钩子     ≤ 10 条 × 60 字
     常驻合计    ≤ 1.5KB
③ 下潜（按需，模型调用 soul_detail）
     ≤ 2 次，每次 ≤ 1000 字
```

**②和③分离**：大多数问题在钩子层答完；只有"那天具体说了什么"才下潜。

## 6. 索引前提（否则数据量一大就卡）

| 索引 | 用途 | 现状 |
|---|---|---|
| `fact_slots(entity_id)` | 实体时间线 | ✅ 已有 |
| `facts.created_at` / `at` | 时间窗 | ⚠️ 无索引 |
| 全文索引（中文要另想办法，见下） | 谓词与相关式 | ❌ 没有 |
| `access_count` / `last_access_at` | 衰减与强化 | ❌ 没有 |

**不换数据库**：这三样 SQLite 都能做，撑到百万行。

### 6.1 实测：FTS5 能用，但中文的 2 字词它搜不到

Node 内置 SQLite 3.51.2 **带 FTS5**（`CREATE VIRTUAL TABLE ... USING fts5` 成功）。但两种分词器对中文的表现是：

| 查询 | `trigram` | `unicode61` |
|---|---|---|
| 火锅（2 字） | **0 条** | 0 条 |
| 吃了火锅（4 字） | 1 条 | 0 条 |
| 下雨了（3 字） | 1 条 | 0 条 |
| 换了工作（4 字） | 1 条 | 0 条 |

- `unicode61` 把整段中文当一个 token（没有空格），基本不可用。
- `trigram` 只索引连续的 3 字窗口：**2 字词永远搜不到**，而中文最常用的正是 2 字词（吃饭、下雨、吵架）。

**结论**：不要直接拿 FTS5 当全文索引。可行的两条路：

1. **自建二元索引**（推荐）：一张 `(gram, fact_id, count)` 表，写入时把中文切成 2 字窗口，查询时按 gram 取交集。这正是现在 `scoring.ts tokenize()` 已经在做的事，只是从内存搬到表里，支持增量与排序。
2. FTS5 `trigram` 只用于 ≥3 字的谓词，2 字词回落到 LIKE。

**当前阶段**：事实只有几十条，现在的内存 BM25 足够；这条留到数据量真的上来再做，但**别以为 FTS5 是免费午餐**。

## 7. 降级规则（没有谓词索引时）

"上次和 a 吵架"里"吵架"若无索引：

```
实体取到 a 的最近 N 条 → 在这 N 条里做文本匹配 → 命中就给，未命中就说没有
```

**绝不做的事情**：拿别的实体的记忆来凑。**"没有"是一个合法答案。**

## 8. 验收

| # | 用例 | 期望 |
|---|---|---|
| 1 | 上次和 a 吃饭是什么时候 | 命中 a 的那条；不得返回其他线索 |
| 2 | 上次和 c 吃饭是什么时候 | 明确说没有 |
| 3 | 上次聊到哪 | 上一闭合线索 |
| 4 | 上周下雨那天我在做什么 | 时间窗召回，带出当天的事实 |
| 5 | 常驻注入总量 | ≤ 1.5KB |
| 6 | 压测：3.6 万轮 / 1 万事实 | 实体/时间 p95 < 20ms，全文 p95 < 50ms |

**第 1、2 条一票否决**——错主体是记忆系统最严重的错误：它会把关于别人的事说成关于你的。

## 9. 开放问题

| 问题 | 现状 |
|---|---|
| 实体别名（"她"指谁） | 未处理，只能按全名匹配 |
| 一句多实体（"a 和 c 那次"） | 未定义，先按第一个匹配 |
| 谓词索引粒度（type_name 还是 FTS） | 先 FTS，观察命中率 |
| 路由认错时如何自愈 | 退化为相关式；日志记 `router=fallback` |

## 10. 实施顺序

```
1. access_count / last_access_at + 时间索引（小，先做）
2. latestAbout(entity, {predicate, limit}) + latestThread()
3. 路由（规则）+ 日志 router=...
4. FTS5
5. 注入改漏斗（钩子优先，下潜按需）
6. 压测脚本
```

前两步就能让"上次和 a 吃饭"答对——**先修那个实测错误，再谈架构。**
