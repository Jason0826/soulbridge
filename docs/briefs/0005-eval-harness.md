# 需求说明：评估 harness（让"记忆有没有用"可测）

- 状态：Draft
- 日期：2026-10-29
- 后续：RFC（待写）、ADR 0010（单臂评估）、ADR 0018（成长判据）、`thesis.md` P1

---

## 1. 一句话目的

把"记忆到底有没有用"从主观感受变成**可重复执行的数字**，并在 P3 四臂实验之前，先能回答一个更小的问题：**注入得对不对**。

## 2. 现状与问题

1. **没有任何测试消费模型回答**。现有 `packages/core/test/*` 全是纯函数与不变量测试；`context()` 只被断言"预算/used/不截断"，没人验证它注入的内容**帮着答对了没有**。
2. **ADR 0010 定了单臂 ON/OFF，但只有口径，没有 harness**。ON/OFF 两臂怎么建、结果怎么算，都还空着。
3. **尺子本身有前科**。真机观察：affect 黄金集 dev 40/40、holdout 20/20 全过，7 句真实口语 6 句零命中。**通过了测试，不等于测到了使用场景。**
4. **可复用的素材在隔壁**。`soulkernel-rs/tests/eval/memory/`（本机 `D:\git-workspace\repos\soulkernel-rs`，不在本仓库）有 59 个 case、一套 `seed → probe → assert` 结构、以及一份记录了"尺子怎么骗人"的 README。**不能直接搬**，原因见 §3。

## 3. 为什么不能直接搬那 59 个 case

| 缺口 | 数量 | 说明 |
|---|---|---|
| KG 能力 | 8 | soulbridge 没有知识图谱 |
| `chunks` 能力 | 4 | 没有原始对话块 |
| 主动提醒 | 3 | 没有 reminder |
| 多用户隔离 | 5 | 单 `soulId`/`userId`，无 scope 概念 |
| LLM judge 断言 | 29 | 需要裁判 harness，当前一个都没有 |
| 特殊检查器 | 3 | `kg_edge_count` / `kg_entity_merge` / `reminder_date` |

**最根本的一条**：59 个 case 全部断言 **agent 的回答**，而 soulbridge 只产生 **注入文本**。缺的不是格式转换，是**消费者**。

## 4. 消费者与决定

| 消费者 | 什么时候 | 要做什么决定 | 需要什么信息 |
|---|---|---|---|
| S2 阶段 | 开工前 | 纠正闭环做完有没有效果 | 同一批 case 的前后数字 |
| P1 实验（P3 做） | 四臂对比 | 人格层是否随窗口变大保持优势 | ON/OFF 归因 + lift |
| 用户（判据 1、3） | 每周 | 这一周是不是真的少重复了 | 重复提问/纠正复发计数 |
| 发版 | `npm test` 前 | 这次改动有没有让记忆变差 | 归因通过率不下降 |

## 5. 需求

| 级别 | 需求 | 验收方式 |
|---|---|---|
| **必须** | 一批 case 跑 ON（有记忆）/ OFF（空 soul）两臂 | 输出 `on_pass_off_fail` / `both_pass` / `both_fail` / `mem_hurts` 四象限计数 |
| **必须** | 归因口径：只有 `ON 过且 OFF 挂` 才算记忆的功劳 | 与 soulkernel 的 `ablation` 语义一致 |
| **必须** | 断言分层：字符串断言优先，judge 只做兜底 | 每条 case 标注用了哪一层 |
| **必须** | 可复现：同 commit 连跑两次，归因方向一致 | 记录两次的差异，写进 README |
| **应该** | 复用 soulkernel 的 case schema（`seed/probe/assert/ablation`） | 能直接读同一份 JSON 结构 |
| **应该** | case 的终态**不可猜**（防止 OFF 臂靠默认值蒙对） | 每个 case 有 note 说明为什么猜不到 |
| **不做** | 多用户 / KG / chunks / reminder 类 case | 默认跳过，`--filter` 不可选 |
| **不做** | 把真实模型调用放进 CI 门禁 | 手动触发，成本不可控 |

## 6. 非目标

- 不解决"记忆是否让人格更连续"（那是 P3 四臂的事，需要 8k/128k/1M 三档，见 thesis §4）
- 不做性能压测
- 不评估 affect（词表覆盖问题已单独记在 S1 观察记录）
- 不替代人工判据 1 和 3

## 7. 成功判据（可执行）

```
npm test                          → 现有单测全绿，一条不降
<harness> --arm=off,on --n=1      → 四象限计数表，0 个 infra_error
同一 commit 连跑 2 次              → mem_helps 的方向一致（数量可抖动）
<harness> --filter=recall         → 只跑可用的子集，且不因缺能力而误报失败
```

## 8. 前置条件与时机

- **什么时候可以实施**：S1 收尾之后（2026-11-05 或预算用尽）。现在动会污染正在进行的观察。
- **依赖**：
  1. 一个消费者：stub 模型（读注入文本作答）**或** 真实模型会话（只能观察，不可自动）
  2. 两个隔离的 soul home（ON 臂 / OFF 臂），不碰真机库 `~/.soulbridge/soul.db`
- **什么情况下不做**：
  - S1 的判据 1 和 3 拿不到可用数据（那说明连"用起来有没有感觉"都测不了，先解决那个）
  - 消费者方案定不下来，最后退化成"只测注入文本"——那时它就不是 harness，是单测，应改名

## 9. 开放问题

1. **消费者选哪个**：stub 模型（可控、便宜、但测不到模型实际怎么用注入）vs 真实模型（真实、贵、不可复现）？
2. **judge 的可信度**：soulkernel 记过"judge 对多条件/否定判不稳"。要不要先做 judge 与人工标注的一致性验证？
3. **case 数量**：先跑多少条算有意义？soulkernel 的经验是 52 条 × N=3，抖动仍明显。
4. **两臂怎么隔离**：soulbridge 是单用户，ON/OFF 需要两个独立 DB 文件还是两个 `soulId`？后者更接近"同一用户的空白版"。
5. **要不要先做"注入内容断言"这一层**：它测的是 soulbridge 自己的职责（注入对不对），比回答断言便宜一个数量级，但证明不了"有用"。

## 10. 附：soulkernel case 结构（供设计时参考）

| 维度 | 分布 |
|---|---|
| 类别 | recall 23 · temporal 9 · honesty 8 · no_repeat 7 · scope 5 · dedup 4 · proactive 3 |
| seed | conversation 27 · 直接塞记忆 20 · KG 8 · chunks 4 |
| 断言 | LLM judge 29 · 特殊检查器 3 · 纯字符串 27 |

值得照抄的四条尺子规则（来自那份 README 的踩坑史）：

1. **seed 与 probe 故意错开措辞**，否则测不出"相关 ≠ 字面重叠"
2. **双臂消融**：通过 = `ON 过且 OFF 挂`，否则不算记忆的功劳
3. **终态必须猜不到**：默认值/乐观猜测能命中的 case，长期只会报 `both_pass`
4. **子串断言分不清"提到"和"泄露"**：`must_not_contain` 会把正确答案判错，需要 judge 规则
