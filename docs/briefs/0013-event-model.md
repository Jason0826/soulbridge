# 需求说明：事件模型（用公开标注体系验证）

- 状态：**Superseded（2026-11-02，→ ADR 0032 两层记忆）**
- 日期：2026-11-01
- 关联：[0011 会话层](0011-conversation-layer.md)、[0012 人物层](0012-people-layer.md)、[0009 §4.6](0009-schema-redesign.md)
- 验证数据：DuEE 1.0 事件 schema（65 类事件 / 121 角色），来源 `data/DuEE1.0/duee_event_schema.json`

## 1. 为什么要这份

之前的模型是**从 30 个问题推的**，只覆盖"我关心的"，不覆盖"世界会出现的"。
用公开标注体系做一次结构验证，看字段够不够装真实语料。

## 2. 数据（实测）

### 2.1 全量 65 类

| 指标 | 数值 |
|---|---|
| 事件类型 | 65 |
| 角色槽位总数 | 217 |
| 不重复角色名 | 121 |
| 平均每类角色数 | 3.34 |
| `时间` 出现 | **65/65（100%）** |
| `地点` 出现 | 14/65（**21.5%**） |
| 只出现 1 次的角色名 | **112/121（92.6%）** |

### 2.2 个人生活子集（人生 12 / 交往 5 / 组织关系 8）

| 指标 | 数值 |
|---|---|
| 事件类型 | 25 |
| 角色槽位 | 73 |
| `时间` | **25/25（100%）** |
| `地点` | 4/25（**16%**） |
| 不重复角色 | 44 |
| 只出现一次 | **40/44（91%）** |

### 2.3 角色名长什么样

```
出售/收购   出售方 · 交易物 · 出售价格 · 收购方
辞/离职     离职者 · 原所属组织
道歉        道歉者 · 道歉对象
裁员        裁员方 · 裁员人数
涨价        涨价方 · 涨价物 · 涨价幅度
```

**这些不是 agent/patient 这类通用角色，是每类事件自带的槽位。**

## 3. 结论

1. **时间必填**（100%）、**地点可省**（16–21%）：此前的判断被数据支持。
2. **角色不能是全局枚举**：91–93% 的角色名只出现一次 → 角色属于"事件类型的框架"，不属于全局。
3. **有一类槽位不是实体**：`死亡人数`、`裁员人数`、`涨价幅度`、`刑期`——是数值。
4. **事件类型词表可用 25 类个人生活事件起步**，比凭空列强。

## 4. 模型

### 4.1 三张表

| 表 | 职责 |
|---|---|
| `entities` | 谁能被提到（人 / 物 / 地点 / 自己） |
| `facts` | 发生了什么（一次事件、一个状态、一个承诺） |
| `fact_slots` | 事实的槽位：**指向实体**或**字面值**（人数、金额、幅度） |
| `gaps` | 不知道但想知道的事（缺席） |

### 4.2 角色两层的理由

| 层 | 例子 | 用途 |
|---|---|---|
| `slot` | `出售方` / `离职者` / `道歉对象` | 事件类型自带，存原文用语 |
| `core_role` | `agent` / `patient` | 通用查询（"谁和这条有关"） |

**没有 core_role 就无法跨类型查询；只有 core_role 就丢掉 91% 的信息。两层都要。**

### 4.3 为什么槽位与实体合一

`fact_participants` 和 `params` 本来是两张表，但两者结构相同：

```
一个槽 → 要么 entity_id，要么 value
```

合成一张 `fact_slots`，用 `value_type` 区分。少一张表，少一个概念。

## 6. 验收

```
1. 用 25 类个人生活事件编码 20 条真实对话
   → 每条能落到 facts + fact_slots，无"装不下"的句子

2. 取一段小说（20 句）
   → 能编码比例 ≥ 80%；不能编码的，写出缺什么

3. 角色查询
   → "谁和这件事有关"能用 core_role 答；"她被谁裁的"能用 slot 答
```
