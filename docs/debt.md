# 技术债与未收尾的线

> **谁读**：每次决定"下一步做什么"之前；每周一次 review。
> **什么时候读**：感觉"在同时推很多东西"、或者某个功能建好了却从没生效过。
>
> 和 [backlog.md](backlog.md) 的分工：backlog 记**没开始做的**（含启动条件）；这里记**做了但没
> 收尾、或建好了却从未生效**的。数字来自 `node scripts/health-check.mjs`（17 WARN）与
> `soul.db` 实测，2026-11-10 20:50。

| 类别 | 项 | 数 | 说明 |

| 死路径 | 有表/有函数但没有业务调用者 | 4 | `turn_pairs`（97 行历史，无写者）、`supersede()`（**冲突取代是手动 API，不是机制**）、`vividness`、`supersededBy` |
| 退场未完成 | 登记了但没退 | 4 | anchor-container / json-extraction-shape / seed-backfill-write / reset-seals |
| 词表碎片 | 只用过一次的标签 | **322 / 470** | 与 `type_name` 的 466 个值同源 |
| 数据形态 | 实体 id 里 URL 编码了名字 | 170 | 历史数据，非代码错误 |
| 代码质量 | 导出函数没写"边界" | 35 | 另有 3 个函数 >100 行（`openSqlite` **1246 行**） |

## 三、只能人来决定的四件

1. **`holder` 的声明**（`term-audit` 现在就红在这）：改名字变成"层词 + 实体 id"两档，还是补成三层值域？
2. **`type_name` 收不收敛**：466 个值、322 个孤例。它已经不参与路由（ADR 0027），要么**退出提示词**（不再让它生成标签），要么**给它一张受控词表**。
3. **`supersede()` 接上还是删掉**：新结论取代旧结论，现在没有业务路径调用它。
4. **`lesson` 与 `disposition` 二选一**：两者都表示"遇到这种情形该怎么做"，不能都留。

## 四、建议的清偿顺序

**第 0 步，止血（三件，都不写新功能）**

```
a. 停掉 catalog 注入，代码保留     → 每轮省 ≈573 token
b. 消掉 6 组重复声明，全改成引用   → 纯改引用，不动行为
c. 决定缺口机制的命运              → 要么接上"被回答关闭"，要么停开新的
```

**第 1 步，清死路径**：`turn_pairs` 退场、`supersede()` 接上或删、`vividness`/`supersededBy` 定性。

**第 2 步，才轮到 0030**：它现在是"最想做的"，但不是"最该做的"——上面每一条都会在 0030 落地后变成更难拆的债。

## 五、怎么防止再欠

```
1. 每个 brief 顶部写「退场条件」：什么算做完、做完之后哪段代码/文档下台
2. 一条线没写退场条件就不开工；两条以上并行必须在本文登记
3. 每周跑 term-audit + health-check，本文的数字跟着更新；不更新就说明没 review
```
