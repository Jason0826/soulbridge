# 质量模型

> 质量不是"写得漂亮"，是**你愿意为它写测试的那些约束**。
> 没写测试的质量标准都是装饰。

---

## 1. 属性排序（顺序就是取舍）

| # | 属性 | 为什么排这里 | 验收方式 |
|---|---|---|---|
| 1 | **可替换性** | 宿主 API 一年改三次，core 不能跟着改 | 依赖只向内；`core` 的 import 白名单 |
| 2 | **可测试性** | 没有确定性就没有 eval，thesis 落空 | 纯函数 + 注入 clock/rng，逐位可复现 |
| 3 | **可审计性** | 注入进别人的系统提示，必须能追责 | 每条注入有 `used`；每条判断有证据 |
| 4 | **隐私** | 读别人对话，翻车一次就完了 | 不存原文；本地优先；可 `forget` |
| 5 | **运行成本** | `npx` 要秒开 | 冷启动 < 300ms；单轮 < 5ms |
| 6 | **可读性** | 开源的生死线是"陌生人一个下午能改" | core < 3000 行；单文件 < 300 行 |

**没有把性能与"优雅"放前面**：这是一个 IO 密集的旁挂进程，性能不是瓶颈；"优雅"是主观的，容易变成推翻别人设计的借口。

## 2. 自动门禁（ADR 0011）

| # | 门禁 | 命令 / 检查 |
|---|---|---|
| G1 | 类型零错误 | `npm run typecheck` |
| G2 | 公共 API 无 `any` | 类型检查 + 抽查 |
| G3 | `core` 仅 import `node:` | `scripts/check-imports.mjs` |
| G4 | 每个动词有降级测试 | `grep -r "degrade:" packages/core/test` |
| G5 | 不变量测试 | `node --test`（context 预算 / used / 不截断） |
| G6 | 错误模型 | 测试断言 `observe` 不抛 |
| G7 | 日志不含正文 | 负向测试：注入含 `password=` 的文本，断言日志无原文 |
| G8 | 体积 | core < 3000 行、单文件 < 300 行 |
| G9 | 零运行时依赖 | `package.json` 的 `dependencies` 为空 |

## 3. 禁止的反模式

| 反模式 | 为什么禁 | 替代 |
|---|---|---|
| 全局可变状态 | 第二个使用者就炸 | 状态挂在 `Soul` 实例上 |
| loop 内直接写 SQL | 逻辑与存储耦合，无法替换 | 走 `SoulStore` 端口 |
| `catch {}` 静默 | 故障不可见 | 分类后返回错误码 |
| 时间/随机散落 | 测试不可复现 | 注入 `clock()` / `rng()` |
| 提前抽象 | 三处重复才值得抽象 | 先重复，后提取 |
| 魔法数字 | 阈值不可评审 | 命名常量 + 进 spec |
| 在 core 里做 I/O | 破坏可测试性 | 放到 adapter |

## 4. 人工评审清单（五条，每条一句话）

1. **边界**：这个改动放在 core 还是 adapter？依赖方向对吗？
2. **可测**：新增行为有对应测试吗？失败路径测了吗？
3. **可审计**：如果它注入了文本，`used` 能追到吗？如果它做了判断，证据在哪？
4. **隐私**：有没有把用户原文写进日志、错误信息或存储？
5. **减法**：这个改动能不能用"删掉某处"代替"新增一处"？

五条里任何一条答不上来，PR 不合并。

---

## 5. 质量预算

不是越高越好，是有上限的：

| 预算 | 上限 | 超了怎么办 |
|---|---|---|
| core 代码行数 | 3000 | 拆包，或删功能 |
| 单文件行数 | 300 | 拆分职责 |
| 运行时依赖 | 0 | 先写 ADR，再考虑 |
| 冷启动 | 300ms | 延迟加载词库/DB |
| 单轮开销 | 5ms | 缓存 + 纯函数 |

**预算的意义是强制取舍**，不是鼓励无限优化。
