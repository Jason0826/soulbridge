# Claude Code 的记忆模式：对照、可借鉴、我们更好的地方

> 状态：参考（2026-11-08）——**不是决定，当前不改实现**。
> 来源：[code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory)、
> [context-window.md](https://code.claude.com/docs/en/context-window.md)、
> [sub-agents.md](https://code.claude.com/docs/en/sub-agents.md)（2026-11-08 抓取，Claude Code v2.1.3xx）。
> 不在此文范围：Anthropic API 层那个同名的 `memory` tool（beta，客户端 `/memories` 目录 + view/create/str_replace/insert/delete/rename），
> 它是**客户端的工具协议**，与 Claude Code 这套文件体系不是一件事。
> 读者：0029 阶段 1 判决之后做优化轮次的人；任何想问"要不要抄 Claude Code 记忆"的人。
> 用途：§2 逐条排期，§3 当作自评的底稿，§5 是明确的"不抄"。

## 0. 它到底是什么（三十秒版）

两套 markdown 文件，**每次会话开头全量拼进上下文**：

```
CLAUDE.md   你写：四层作用域（托管 / 用户 / 项目 / 本地）+ 目录树向上递归 + 子目录按需 + .claude/rules/ 路径作用域
auto memory 它写：~/.claude/projects/<project>/memory/ 下 MEMORY.md 索引 + 一条一个主题文件
```

没有向量检索、没有 embedding、没有后台归纳。**"记忆"就是一组能被重新读回来的文件。**

三个关键数字：

| 项 | 值 | 含义 |
|---|---|---|
| `MEMORY.md` 注入量 | 前 **200 行** 或 **25KB**，先到先算 | 索引有硬上限，超出部分**下次加载直接丢弃** |
| 超限的处置 | 写成功后测量，超了**返回错误让模型重写索引** | 不是警告，是让它自己修 |
| 主题文件 | 启动**不读**，靠模型用普通文件工具按需 `Read` | 索引常驻、正文按需 |

auto memory 每条带一个 `type`（`user` / `feedback` / `project` / `reference`），写文件时自动补 `modified`
（ISO 8601）——**它只有"改于何时"，没有"事实何时成立"**。目录机器本地，同仓库的 worktree 共享，不跨机。

压缩（`/compact`）之后哪些东西回来，它列了一张表，其中与我们直接相关的两行：

| 机制 | 压缩后 |
|---|---|
| 项目根 CLAUDE.md、无 `paths:` 的 rules | **从磁盘重注入** |
| Auto memory | **从磁盘重注入** |
| 带 `paths:` 的规则、子目录 CLAUDE.md | 按需重载（等于被摘要掉了） |

**这两行是它整套设计里最实用的一招**：因为记忆是文件，所以压缩后能重新读回来；对话里的东西一旦压掉就没了。

## 1. 对照总表

| 维度 | Claude Code | soulbridge（现状，有出处） | 判断 |
|---|---|---|---|
| 载体 | markdown 文件（人可读、可 git） | SQLite `soul.db` + 文件队列（`pending-*.json`） | 各有胜负，见 §2.4 / §3.6 |
| 索引形态 | `MEMORY.md` 前 200 行 / 25KB，**硬上限** | `<catalog shown total>` ≤20 条（`CATALOG_LIMIT`），索引句"≤30 字"只是 prompt 要求，**代码不截断** | **它更好**（§2.1） |
| 索引排序 | 无排序，靠人/模型维护顺序 | `recall_count` → `confidence`（0029 §四，"复现频率"是可算的那一半） | **我们更好** |
| 正文读取 | 模型用 `Read` 读主题文件 | `soul_detail(id)` / `soul_recall(关键词)`，写 `tool-call` 事件 | **我们更好**（可观测） |
| 注入时机 | **会话启动一次** + 压缩后重载 | **每轮 pre-step 从库里读**（`buildRelatedContext`） | **我们更好**（§3.1） |
| 系统提示词 | CLAUDE.md 当 **user message** 注入，不是 system prompt | 同：system 段只放身份+语气，易变内容走 pre-step（`in-history` provider 语义） | 打平，且理由一致 |
| 写入权 | 模型自己决定写，**无闸门、无证据要求** | 离开点整段抽取 → 闸门 → candidate/active → 分类（0018/0028/0033） | **我们更好**（§3.2） |
| 时间 | 只有 `modified` | `valid_from` / `valid_to` + 精度 day/range/unknown（0027） | **我们更好**（§3.3） |
| 分层 | 4 个 `type` 标签，平铺 | 事实 / 规则（带触发）/ 画像（带维度准入）三层（0033） | **我们更好** |
| 作用域 | 四层 + `paths:` 路径作用域 | **没有 scope**，排序只能靠复现频率（0029 开放问题 4） | **它更好**（§2.2） |
| 强制力 | 明说"是 context 不是 config"，要强制用 `PreToolUse` hook | `<rules fired>` 读作要求，但同样只是 prompt 级 | 打平，但它更诚实 |
| 子代理 | 主会话 auto memory **不注入**子代理；fork 例外 | 子代理各自开轮、事件流无谱系；是否注入了主记忆**没验过** | **它更好**（§2.5） |
| 预算治理 | 索引硬上限 + 超限报错 | 分块上限：catalog 20 / time-window 10 / rules 5 / anchor 3 / profile 8；但 `<related>` **明确无上限**（代码注释写了理由） | 各有欠账 |
| 跨人跨工具 | per-repo 文件，换工具带不走 | 单库、跨项目，但绑在 DSH 插件上 | **我们方向对**（§5） |

## 2. 值得借鉴的点（按优先级）

| # | 它的做法 | 落到我们哪里 | 验收 |
|---|---|---|---|
| 1 | **索引有硬上限，超限时报错让模型自己重写**（200 行 / 25KB；写成功也照样测量） | `renderCatalog`：① 给目录句加**机器**长度上限（现在是 prompt 里的"≤30 字"，代码不截断，`state.md` 已经把它登记成观察项）；② 给整块加字符预算，超了按条数砍并**计数可见**；③ 砍不动就 trace 一条 `catalog-over-budget` 并让下一次"补索引"批次带超限理由重写 | 注入块 chars 有显式上限；构造一个 80 条 × 60 字的夹具，断言超限后仍 ≤ 预算且 trace 一条；下轮索引句变短（活证据，不是只有测试） |
| 2 | **作用域分级**：个人偏好 / 这个仓库的约定 / 这次任务的临时决定，加载与排序都先按作用域分 | 不抄四层文件；抄**字段**：每条规则/事实带 `scope`，目录排序与注入先按"当前仓库/用户全局"过滤。这正是 0029 开放问题 4，现在只能拿 `recall_count` 当排序 | 同一个词在两个仓库问，命中的是不同的规则；`catalog-stats` 能按 scope 分组读出命中率 |
| 3 | **压缩后重载**被列成一张逐项验证的表（what survives compaction） | 我们构造上更稳（每轮重读），但**没有对应的回归测试**。补一条：模拟 `compaction/end` 后第一轮 pre-step，断言 profile / catalog / anchors / 时间窗全部回来，且 ledger、handoff、sealed 段状态各自正确 | 一条集成测试从绿变红（删掉重读接线就红）；不靠"我们知道它是每轮注入"这种口头保证 |
| 4 | **人可读**：全是纯 markdown，用户随时打开、改、删、git diff | 我们只有 CLI/SQL。加一个**导出视图**（`soulbridge export --memory` 或 `/memory` 式浏览）——定位是渲染，不是第二份权威（AGENTS 第 5 条） | 导出文件里每条带 id + 索引句 + 最后复现时间；改它不影响库（单向） |
| 5 | **子代理的记忆边界是显式的**：主会话 auto memory 不进子代理，要就给子代理单独开 | 先实测：我们的 `agent/pre-step` 对子代理是否同样注入？若是，等于把用户画像塞给每一个一次性 worker——浪费注意力，还可能让子代理"以为自己是主会话" | 一次真子代理跑，看 `prestep` 日志里有没有它；有就定一条边界（注入什么、不注入什么），没有就把结论写进 `dsh-runtime.md` |
| 6 | 每条记忆带**新鲜度**给模型看（`modified`） | 我们有 `valid_from` 和 `recall_count`，但注入时**没有把"这条多久没被复现"给模型看**。目录句里加一个极短标记（如最近复现的日期或"未复现"）可能比排序更有用 | 观察项，不排期：先看 §2.1 改完目录的大小，再决定要不要加字段（加字段 = 加 token） |

### 次要的（有场景再做）

| 做法 | 可借鉴处 |
|---|---|
| `@path` import（最多四跳、外部路径要批准） | 反面教材：**import 是展开加载，不省 token**，只组织文件。我们的提示词分层别走这条路，走 SeeCode 那套"按需读" |
| `InstructionsLoaded` hook 记录"谁在何时被加载、为什么" | 我们的注入已经有 trace（catalog / rule_fired / router / time_window），差的是"为什么是这 20 条"——排序依据（recall_count、confidence）没进 trace |
| `/doctor prompt-audit` 让模型审自己的指令文件：过期、指向不存在的文件、互相矛盾 | 相当于给我们 194 条规则做一次"过期/矛盾"审计，判据是人判不是机器判——先有数字再说 |

## 3. 我们做得更好的地方（带证据）

### 3.1 注入不依赖"启动"这个时机，所以压缩/重启/换会话都杀不掉它

它是"启动注入 + 压缩后从磁盘重载"——**重载是补丁**：文件没变才成立，压缩期间模型写过的内容只能靠文件本身的 mtime 兜。
我们是 `agent/pre-step` 每轮从库里读（`index.js` 的 `buildRelatedContext`），
压缩发生与否不影响下一轮注入什么；账本还是内存态时我们专门做过一次**从 trace 全量重放**（插件 0.0.125）来扛重启。
**构造上不依赖时机，比事后补一次重载稳。**

### 3.2 写入有闸门、有证据、有撤回语义

- 教训先落 `candidate`，分类器给触发槽才 `active`（0018 §九 3、schema v17）；
- 规则由"能触发的集合"定义，不由中文类型名定义（B0 三个洞就是这条的代价）；
- 纠正只是候选（待核），转正要复现或确认；错判用 supersede 保留记录。

它那边是"模型觉得值得记就记"，没有证据门槛、没有复核状态、没有撤回——**记错了只能靠人翻文件发现**。

### 3.3 时间轴是结构，不是备注

`valid_from` / `valid_to` + 精度（day / range / unknown）+ "日历日只有一种存法：UTC 零点"。
它只有 `modified`：**"这条什么时候改的"不等于"这件事什么时候成立的"**。
差别在检索：它算不出"上周发生了什么"，我们算得出（`<time-window>`，还有"空窗口明确说没有记录"）。

### 3.4 记忆被用了没有，是可数的

`<catalog>` + `soul_recall` / `soul_detail` → `tool-call` 事件 → `catalog-stats.mjs` 的判决线
（调用次数 >0 且抽样相关率 ≥70%）。**它没有等价物**：auto memory 有没有被读、读了有没有用，只能靠人感觉。
`state.md` 里"调用 0 次"这个数本身就是产物——**0 也是结论**，它决定进阶段 2 还是继续。

### 3.5 分层带关系，不是四个标签

事实 / 规则 / 画像三层，规则带触发槽、画像带维度准入（0033）。它的 `type` 是标签，**标签之间没有关系**：
一条 `feedback` 和一条 `project` 之间既不冲突也不推导。

### 3.6 注入块是转义过的，正文不能伪造结构

`escapeBlockText` + 注释写明"规则语句来自用户原话，不转义就能关掉块、伪造一条要求"。
它的 CLAUDE.md 也是当 user message 注入，但文档没有提到块边界与转义——**这条我们至少是显式做了的**。

## 4. 它明确的取舍，我们不该学的那一半

| 它的做法 | 为什么不抄 |
|---|---|
| 四层文件作用域（托管/用户/项目/本地）+ 目录树拼接 | 我们是插件，不接管仓库文件；仓库约定归仓库（ADR 0019）。抄"作用域字段"，不抄"接管目录" |
| **per-repo 一份记忆** | 方向相反：那正是用户痛点——换个仓库、换个工具就要重讲一遍原则 |
| 全量拼接、无排序 | 194 条规则全量拼 = 墙纸；我们已经有"目录 ≤20 + 排序"这条经验 |
| `@path` 递归 import | 展开加载不省 token，只是把大文件拆开 |
| 让模型自由写文件、无闸门 | 与 ADR 0027 / 0031 冲突：判断归模型，但形态和写入必须过闸门与地板 |

## 5. 排期建议

```
先做（都是"已有代码，缺一条约束或一次实测"）
  1  目录硬上限 + 超限自我修复（§2.1）——state.md 已登记为观察项，正好收口
  5  子代理注入边界实测（§2.5）——一次真子代理就能定性，不定性就别写设计
  3  压缩后注入回归测试（§2.3）——把"我们知道"变成"它测得出"

后做
  2  scope 字段（§2.2）——等 0029 阶段 1 判决；现在改排序会污染对照臂
  4  导出视图（§2.4）——低成本，不占主线，随时可插

不排期
  6  新鲜度进目录（§2.6）——先看 1 改完目录多大，加字段 = 加 token
```

## 6. 一句话结论

**它是"能被重新读回来的文件"，我们是"能算出数的库"。**

- 结构（注入时机、写入闸门、时间轴、可观测）：我们更好，而且是原理性的，不是实现细节。
- 工程卫生（硬上限、作用域、人可读）：它更好，而且**恰好都是"硬"的东西**——硬上限、硬作用域、硬可读。

所以下一步该补的不是再加一层模型判断，而是它那三个"硬"：**索引有预算、记忆有作用域、内容人读得懂**。
